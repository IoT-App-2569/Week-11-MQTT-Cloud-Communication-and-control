##  การทดสอบและการตรวจสอบผลลัพธ์ (Testing & Verification)

1. แฟลชโปรแกรมลงบนบอร์ด ESP32
   ```powershell
   idf.py -p COMx flash monitor
   ```
2. สังเกตผลในหน้าต่าง Serial Monitor
   * บอร์ดเชื่อมต่อ Wi-Fi สำเร็จ
   * เริ่มกระบวนการจับมือ TLS `Connecting to 192.168.1.100:8883...`
   * หน้าจอรายงาน `MQTTS TLS Handshake Successful! Connected to Secure Broker.`
3. สังเกตหน้าต่าง Broker Log
   * Mosquitto จะพิมพ์ข้อความยืนยัน `Peer certificate verified: /C=TH/ST=Bangkok/O=IoT Node/CN=esp32-secure-node`
   * แสดงว่า Broker ได้ทำการตรวจความถูกต้องของใบรับรองบอร์ด ESP32 ผ่านเรียบร้อยแล้ว

##  คำถามท้ายการทดลอง (Post-Lab Questions)
### ข้อ 1: เพราะเหตุใดในคำสั่งสร้าง Server CSR ค่า Common Name (CN) จึงต้องระบุเป็น IP Address หรือ Hostname ของ Broker ให้ตรงกันพอดี? หากระบุเป็นชื่ออื่นจะเกิดข้อผิดพลาดใดขึ้น?
**ตอบ:**  
* **สาเหตุที่ต้องระบุให้ตรงกัน:** เพื่อป้องกันการโจมตีแบบ Man-in-the-Middle (MitM) ตามมาตรฐานโปรโตคอล TLS โดยฝั่ง Client (ESP32) จะนำ IP Address หรือ Hostname ที่ใช้เชื่อมต่อ ไปเปรียบเทียบกับค่า Common Name (CN) หรือ Subject Alternative Name (SAN) ในใบรับรอง (Server Certificate) ที่ส่งมาจาก Broker ว่าตรงกันหรือไม่
* **ข้อผิดพลาดที่เกิดขึ้นหากไม่ตรงกัน:** กระบวนการ TLS Handshake จะล้มเหลวทันที และบน ESP32 จะรายงานข้อผิดพลาดประเภท **`MBEDTLS_ERR_X509_CERT_VERIFY_FAILED`** หรือ **`Hostname Verification Failed`** ส่งผลให้อุปกรณ์ปฏิเสธการเชื่อมต่อกับ Broker นั้นเนื่องจากมองว่าเป็น Broker ปลอมแปลง

### ข้อ 2: การยืนยันตัวตนแบบ Mutual Authentication (mTLS) แตกต่างจากการใช้ HTTPS ทั่วไปบนเว็บเบราว์เซอร์อย่างไรในประเด็นเรื่องใบรับรองฝั่ง Client?
**ตอบ:**  
ความแตกต่างหลักอยู่ที่ **การยืนยันตัวตนแบบสองทาง (Two-Way Verification) ผ่าน Client Certificate:**

* **HTTPS ทั่วไป (One-Way TLS):** ตรวจสอบใบรับรองเฉพาะฝั่ง Server เท่านั้น (เบราว์เซอร์เช็กว่าเว็บเป็นของจริงหรือไม่) ส่วนการยืนยันตัวตนของผู้ใช้งาน (Client) จะใช้ Username/Password, Cookie หรือ Token ในระดับ Application Layer
* **Mutual TLS (mTLS):** มีการตรวจสอบใบรับรองทั้งสองฝั่ง (Two-Way Authentication) โดยที่ **Broker ต้องร้องขอและตรวจสอบ Client Certificate / Private Key จากฝั่ง ESP32 ด้วย** หาก ESP32 ไม่มีใบรับรองที่ออกโดย CA ที่ Broker เชื่อถือ โฮสต์จะไม่ยอมให้สร้างการเชื่อมต่อตั้งแต่ระดับ Transport Layer (ไม่ต้องรอไปเช็ก Username/Password)

### ข้อ 3: หากมีผู้ไม่หวังดีขโมยไฟล์เฟิร์มแวร์ไบนารี (`.bin`) ของบอร์ด ESP32 ไปได้ เขาจะสามารถกู้คืนไฟล์ `client.key` ได้หรือไม่ และในระบบ IoT เชิงพาณิชย์เรามีฮาร์ดแวร์ความปลอดภัยใดมาช่วยแก้ไขปัญหานี้?
**ตอบ:**  
* **การกู้คืนไฟล์ `client.key`:** **สามารถทำได้** หากไฟล์ไบนารี `.bin` ไม่ได้ผ่านการเข้ารหัสไว้ ผู้ไม่หวังดีสามารถใช้เครื่องมือ Reverse Engineering (เช่น Reverse Hex Dump หรือโปรแกรมดึงข้อมูลสตริง) แงะและกู้คืนไฟล์ `client.key` ที่ฝังอยู่ในแฟลชเมโมรีออกมานำไปใช้ปลอมแปลงเป็นอุปกรณ์ตัวนั้นได้
* **ฮาร์ดแวร์และฟีเจอร์ความปลอดภัยที่ใช้ป้องกันในระบบเชิงพาณิชย์:**
  1. **ESP32 Flash Encryption:** เข้ารหัสข้อมูลทั้งหมดในหน่วยความจำ SPI Flash ด้วยคีย์ฮาร์ดแวร์ ทำให้ไม่สามารถอ่านไฟล์ `.bin` จากภายนอกได้
  2. **ESP32 Secure Boot:** ตรวจสอบลายเซ็นดิจิทัล (Digital Signature) ของเฟิร์มแวร์ก่อนบูต เพื่อป้องกันการแก้ไขหรือยัดไส้เฟิร์มแวร์ปลอม
  3. **Digital Signature Peripheral (DS) / Secure Element:** ฮาร์ดแวร์พิเศษใน ESP32 ที่ใช้อ่านและประมวลผล Private Key ภายในพื้นที่ปลอดภัย (eFuse) โดยตรง ทำให้ตัว Private Key ไม่เคยถูกโหลดออกมาใน RAM หรือแสดงในรหัสเฟิร์มแวร์เลย
