เปิดเทอร์มินัลใหม่บนคอมพิวเตอร์

```powershell

pip install esp-rainmaker-cli

rainmaker.py login

rainmaker.py setparams --nodeid <YOUR_NODE_ID> '{"Living Room Light": {"Power": false}}'
```

## 5. คำถามท้ายการทดลอง (Post-Lab Questions)
### ข้อ 1: ในสถาปัตยกรรม ESP RainMaker กระบวนการ Assisted Claiming ช่วยแก้ปัญหาเรื่องการติดตั้งใบรับรองความปลอดภัย (Security Certificates) บนอุปกรณ์ในขั้นตอนพัฒนาต้นแบบได้อย่างไร?
**ตอบ:**  
* **ปัญหาเดิม:** ในการสื่อสาร MQTTS/TLS ปกติ การติดตั้ง Certificate และ Private Key ลงบนอุปกรณ์แต่ละตัวต้องทำผ่านกระบวนการ Manual โดยใช้ OpenSSL สร้างไฟล์คีย์และแฟลชลงเมโมรีรายตัว ซึ่งยุ่งยากและเสียเวลามากในช่วงพัฒนาต้นแบบ (Prototyping)
* **การแก้ไขด้วย Assisted Claiming:** ระบบจะใช้ประโยชน์จากบัญชีผู้ใช้ (RainMaker Account) และแอปพลิเคชันบนมือถือเป็นตัวกลาง โดยเมื่อเริ่มลงทะเบียนอุปกรณ์ แอปมือถือจะส่งคำร้องขอ Claiming ไปยัง ESP Claiming Service บน AWS Cloud เพื่อให้ออก Certificate เฉพาะตัวของ Node นั้น ๆ แล้วส่งกลับมาแฟลชบันทึกเก็บในพื้นที่ NVS (Non-Volatile Storage) ของ ESP32 ผ่านบลูทูธ (BLE/Wi-Fi Provisioning) โดยอัตโนมัติ ทำให้นักพัฒนาไม่ต้องสร้างหรือจัดการไฟล์ Certificate เองแม้แต่ชิ้นเดียว

### ข้อ 2: เพราะเหตุใดฟังก์ชัน `write_cb` จึงต้องเรียกคำสั่ง `esp_rmaker_param_update_and_report()` ทุกครั้งที่มีการเปลี่ยนแปลงค่าพารามิเตอร์?
**ตอบ:**  
เพื่อทำการ **ซิงค์สถานะปัจจุบันของฮาร์ดแวร์กลับไปยัง Cloud (State Synchronization & Reporting)** ด้วยเหตุผลดังนี้:

1. **ยืนยันผลการทำงานจริง (Acknowledgement):** เมื่อแอปพลิเคชันส่งคำสั่งเปลี่ยนแปลงค่ามายังฟังก์ชัน `write_cb` ตัวบอร์ดต้องควบคุมฮาร์ดแวร์จริงก่อน เมื่อควบคุมสำเร็จแล้วจึงเรียกฟังก์ชันนี้เพื่อรายงานย้ำกลับไปที่ Cloud Broker ว่าอุปกรณ์รับและเปลี่ยนสถานะจริงแล้ว
2. **ปรับปรุงข้อมูลบน Clients อื่น ๆ (Multi-client Sync):** ช่วยให้แดชบอร์ดอื่น ๆ หรือมือถือเครื่องอื่นที่ผูกไว้กับ Node เดียวกัน ได้รับสถานะอัปเดตที่เป็นปัจจุบันในทันที Prevent ปัญหาสถานะบนหน้าจอแอปไม่ตรงกับความเป็นจริงของฮาร์ดแวร์ (State Mismatch)

### ข้อ 3: เปรียบเทียบความแตกต่างระหว่างการพัฒนาอุปกรณ์ IoT ด้วย Plain MQTT บน Mosquitto เอง (ในแล็บ 11.2) กับการใช้ ESP RainMaker SDK (ในแล็บ 11.4) ในแง่ของ Development Effort, Security และ Scalability
**ตอบ:**  

| หัวข้อการเปรียบเทียบ | Plain MQTT บน Mosquitto เอง (Lab 11.2) | ESP RainMaker SDK (Lab 11.4) |
| :--- | :--- | :--- |
| **ความพยายามในการพัฒนา<br>(Development Effort)** | **สูงมาก:** ต้องออกแบบโครงสร้าง Topic, จัดการ JSON Parsing, ทำระบบ Wi-Fi Provisioning, และเขียน UI แดชบอร์ดเองทั้งหมด | **ต่ำมาก:** มี SDK สำเร็จรูป, สแกน QR-Code เชื่อมต่อ Wi-Fi ได้ทันที และมีแอปพลิเคชันมือถือแบบ Auto-generated UI พร้อมใช้งาน |
| **ความปลอดภัย<br>(Security)** | **ขึ้นอยู่กับการตั้งค่า:** หากใช้พอร์ต 1883 ทั่วไปจะไม่มีการเข้ารหัส หรือหากทำ TLS เองก็ต้องดูแลความปลอดภัยของ Certificate Server และ Client ทั้งหมดด้วยตนเอง | **สูงมากเป็นมาตรฐาน:** ใช้ MQTTS (TLS 1.2/1.3) และ mTLS พร้อมระบบ Claiming ที่ออก Certificate ปลอดภัยระดับอุตสาหกรรมผ่าน AWS IoT Core |
| **การขยายระบบ<br>(Scalability)** | **จำกัด:** เหมาะกับวงแลนหรือระบบขนาดเล็ก หากต้องการดึงข้ามอินเทอร์เน็ตต้องทำ Port Forwarding, DDNS หรือตั้ง Server Cloud เอง | **ไร้ขีดจำกัด (Serverless Cloud):** ทำงานบน AWS Cloud Infra รองรับการเพิ่มอุปกรณ์เป็นหลักพัน/ล้านตัว สั่งงานข้ามอินเทอร์เน็ตได้ทันทีโดยไม่ต้องตั้งค่า Router |

### ข้อ 4: อธิบายขั้นตอนที่ทำให้ ESP RainMaker สามารถเชื่อมโยงการทำงานร่วมกับระบบสั่งงานด้วยเสียงของ Google Home หรือ Amazon Alexa ได้โดยไม่ต้องเขียนโค้ดเพิ่มเติมบนตัวบอร์ด ESP32
**ตอบ:**  
สาเหตุที่ไม่ต้องเขียนโค้ดเพิ่มเติมบนตัวบอร์ด ESP32 เนื่องจาก **การเชื่อมโยงถูกประมวลผลบน Cloud-to-Cloud Integration** ตามลำดับขั้นตอนดังนี้:

1. **การกำหนด Metadata บนบอร์ด:** ในโค้ดบน ESP32 มีการระบุประเภทของอุปกรณ์ (Device Type) เช่น `esp_rmaker_lightbulb_create()` และพารามิเตอร์มาตรฐาน เช่น `Power`, `Brightness` ไว้แล้วตั้งแต่แรก
2. **การ Mapping ข้อมูลบน Cloud:** ESP RainMaker Cloud จะแปลงโครงสร้างพารามิเตอร์ดังกล่าวให้อยู่ในรูปแบบมาตรฐานของ Smart Home Schema (Google Smart Home Action หรือ Alexa Smart Home Skill) โดยอัตโนมัติ
3. **การผูกบัญชี (Account Linking):** ผู้ใช้เพียงเปิดแอป Google Home หรือ Amazon Alexa แล้วกดเพิ่มบริการ "ESP RainMaker" จากนั้นล็อกอินด้วยบัญชี RainMaker เดียวกัน
4. **กระบวนการสั่งงาน:** เมื่อผู้ใช้พูดสั่งงานด้วยเสียง (เช่น *"Hey Google, turn on the light"*) Google Cloud จะส่งคำสั่งชนิด API ตรงไปยัง ESP RainMaker Cloud แล้ว RainMaker Cloud จะแปลงคำสั่งส่งต่อผ่าน MQTT ลงมายังบอร์ด ESP32 อีกทีหนึ่ง การประมวลผลจึงเกิดขึ้นที่ชั้น Cloud ทั้งหมด บอร์ด ESP32 จึงรันฟังก์ชัน `write_cb` ปกติเหมือนเดิม
