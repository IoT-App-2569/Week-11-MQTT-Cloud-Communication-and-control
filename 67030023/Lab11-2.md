## 4. การทดสอบและการตรวจสอบผลลัพธ์ (Testing & Verification)

> [!IMPORTANT] **ข้อสังเกตและแนวทางแก้ปัญหาสำคัญ (Troubleshooting Guide)**
> 1. **ปัญหา Broker ทำงานซ้ำซ้อน (Split-Brain Broker บน Windows)**:
>    * หากเครื่องคอมพิวเตอร์มีการติดตั้ง Mosquitto เป็น Windows Service ตัว Service ดังกล่าวจะแอบรันอยู่เบื้องหลังและผูกกับ IP `127.0.0.1` ตลอดเวลา
>    * เมื่อท่านเปิดรัน `mosquitto.exe -c mosquitto.conf -v` ใน Terminal อีกตัว บอร์ด ESP32 จะเชื่อมต่อเข้ากับ Terminal (ผ่าน IP วงแลน `192.168.1.xxx`) ในขณะที่คำสั่ง `mosquitto_pub` ที่ส่งไปยัง `127.0.0.1` จะวิ่งไปหา Windows Service แทน ทำให้ส่งคำสั่งไม่ถึงตัวบอร์ด!
>    * **วิธีแก้:** ให้ปิด Windows Service ก่อนเสมอด้วยคำสั่งใน PowerShell (Admin):  
>      `Stop-Service mosquitto; Set-Service mosquitto -StartupType Manual`
> 2. **ทำไมใน MQTT Explorer จึงแสดงเป็น QoS 0 ทั้งที่ส่งด้วย `-q 1`?**:
>    * ตามมาตรฐาน MQTT ระดับ QoS ที่ผู้รับจะได้รับจริงถูกคำนวณจาก **`min(QoS_publish, QoS_subscribe)`**
>    * โปรแกรม MQTT Explorer ทำการ Subscribe ทุกหัวข้อ (`#`) ด้วย **QoS 0** เป็นค่าเริ่มต้น เมื่อ Broker ได้รับข้อความระดับ QoS 1 จึงทำการลดระดับ (Downgrade) เป็น QoS 0 ส่งให้ MQTT Explorer แสดงผล
>    * หากต้องการให้ข้อความปรากฏค้างอยู่ใน MQTT Explorer เสมอแม้ส่งเสร็จไปแล้ว ให้เพิ่มแฟล็ก **`-r` (Retain)** ในคำสั่ง Publish
> 3. **การเปิดพอร์ต Firewall**: ตรวจสอบว่า Windows Defender Firewall อนุญาตให้พอร์ต TCP 1883 รับการเชื่อมต่อจาก Inbound LAN

### 1. การตรวจสอบ Telemetry Data
เปิดเทอร์มินัลบนเครื่องคอมพิวเตอร์ แล้วรันคำสั่งบอกรับข้อมูล (เปลี่ยน `192.168.1.xxx` เป็น IP ของคอมพิวเตอร์ที่รัน Broker):
```powershell
# สามารถใช้ IP ของเครื่อง หรือ 127.0.0.1 (หากปิด Windows Service แล้ว)
mosquitto_sub -h 192.168.1.111 -p 1883 -t "iot/node01/telemetry" -v
```
**ผลลัพธ์ที่คาดหวัง**: จะได้รับ JSON ข้อมูลเซนเซอร์ทุกๆ 4 วินาที
```text
iot/node01/telemetry {"node_id":"esp32-node01","adc_raw":1786,"voltage_v":1.439,"led_state":false,"uptime_ms":1910367}
```
*ทดลองหมุนก้านของ Potentiometer*: สังเกตว่าค่า `adc_raw` และ `voltage_v` เปลี่ยนแปลงตามการหมุนอย่างถูกต้อง

### 2. การส่งคำสั่งเปิด-ปิดหลอดไฟ LED
เปิดเทอร์มินัลอีกหน้าต่างหนึ่ง แล้วทดลองส่งคำสั่งสั่งงาน:

* **คำสั่งเปิดไฟ**
```powershell
mosquitto_pub -h 192.168.1.111 -p 1883 -t "iot/node01/cmd/led" -m "ON" -q 1
```
*สังเกตผล*: หลอดไฟ LED บนบอร์ดจะติดสว่างทันที และในรอบ Telemetry ถัดไป ค่า `"led_state"` จะเปลี่ยนเป็น `true`

* **คำสั่งปิดไฟ**
```powershell
mosquitto_pub -h 192.168.1.111 -p 1883 -t "iot/node01/cmd/led" -m "OFF" -q 1
```
*สังเกตผล*: หลอดไฟ LED จะดับลงทันที และค่า `"led_state"` ใน Telemetry จะเปลี่ยนกลับเป็น `false`

* **คำสั่งแบบ JSON Payload**
```powershell
mosquitto_pub -h 192.168.1.111 -p 1883 -t "iot/node01/cmd/led" -m "{\"state\": 1}" -q 1
```

## 5. คำถามท้ายการทดลอง (Post-Lab Questions)
### ข้อ 1: เพราะเหตุใดเราจึงต้องส่งข้อความสถานะ `iot/node01/status = "online"` ด้วยแฟล็ก `retain = 1` ควบคู่กับการตั้งค่า Last Will and Testament (LWT) ว่า `"offline"`?
**ตอบ:**  
เพื่อรักษาสถิติสถานะการเชื่อมต่อ (Presence Tracking) ของอุปกรณ์ให้สมบูรณ์และถูกต้องอยู่เสมอตามหลักการดังนี้:

1. **ข้อความ `online` พร้อม `retain = 1`:** เมื่อ ESP32 เชื่อมต่อสำเร็จ อุปกรณ์จะส่งสถานะ `online` ค้างไว้ที่ Broker ทำให้ Subscriber หรือ Dashboard ที่เพิ่งเปิดขึ้นมารับรู้ได้ทันทีว่าอุปกรณ์ออนไลน์อยู่ โดยไม่ต้องรอรอบการส่งข้อมูลถัดไป
2. **การทำงานคู่กับ LWT (`offline`):** ตัว LWT ถูกลงทะเบียนไว้กับ Broker ตั้งแต่เริ่มเชื่อมต่อ หาก ESP32 เกิดเหตุขัดข้อง (เช่น ไฟดับ/หลุดวงแลน) Broker จะส่งข้อความ `offline` (ซึ่งควรกำหนดเป็น Retained เช่นกัน) มาทับข้อความ `online` เดิมทันที
การใช้ทั้งสองส่วนคู่กันจึงช่วยให้ระบบส่วนกลางทราบสถานะปัจจุบันที่แท้จริงของอุปกรณ์ตลอดเวลา ไม่ว่าจะเพิ่งเข้ามาดึงข้อมูลตอนไหนก็ตาม

### ข้อ 2: หากเครือข่าย Wi-Fi หลุดชั่วคราว คอมโพเนนต์ `esp-mqtt` มีพฤติกรรมการจัดการอย่างไร และเมื่อสัญญาณกลับมา โค้ดจำเป็นต้องเรียกฟังก์ชันเชื่อมต่อใหม่ด้วยตนเองหรือไม่?
**ตอบ:**  
คอมโพเนนต์ `esp-mqtt` ใน ESP-IDF มีกลไกการจัดการความผิดพลาดอัตโนมัติ (Automatic Reconnection) ดังนี้:
* **พฤติกรรมเมื่อสัญญาณหลุด:** เมื่อ Wi-Fi ขาดหาย ระบบจะแจ้งเตือนผ่าน Event Loop (`MQTT_EVENT_DISCONNECTED`) และเข้าสู่สถานะพยายามเชื่อมต่อใหม่เบื้องหลัง (Automatic Retry Routine) โดยปรับช่วงระยะเวลาเว้นช่วงการเชื่อมต่อ (Exponential Backoff Delay) เพื่อไม่ให้รบกวนทรัพยากรระบบ
* **เมื่อสัญญาณกลับมา:** **ไม่จำเป็นต้องเรียกฟังก์ชันเชื่อมต่อใหม่ด้วยตนเอง** เนื่องจากคอมโพเนนต์ `esp-mqtt` จะทำการ Reconnect กลับไปยัง Broker และสั่งทำการ Re-subscribe หัวข้อ Topic ต่างๆ ที่ตั้งค่าไว้ให้อย่างอัตโนมัติทันทีที่การเชื่อมต่อชั้น IP/Wi-Fi กลับมาใช้งานได้ปกติ

### ข้อ 3: ในฟังก์ชัน `telemetry_task` เพราะเหตุใดหลังจากเรียก `cJSON_PrintUnformatted(root)` แล้วเราจึงจำเป็นต้องเรียกฟังก์ชัน `free(json_str)` และ `cJSON_Delete(root)` เสมอ? หากละเลยจะมีผลเสียอย่างไรต่อหน่วยความจำของ ESP32?
**ตอบ:**  
**สาเหตุที่ต้องคืนพื้นที่หน่วยความจำ:**
1. `cJSON_PrintUnformatted(root)` จะทำการจองพื้นที่หน่วยความจำแบบไดนามิก (Heap Memory ผ่าน `malloc`) เพื่อสร้างสตริง JSON ดังนั้นเมื่อนำสตริงไปใช้งานเสร็จแล้ว ต้องคืนพื้นที่ด้วย `free(json_str)`
2. `cJSON_Delete(root)` ทำหน้าที่ คืนพื้นที่หน่วยความจำโครงสร้างต้นไม้ (Tree Structure) ทั้งหมดที่ถูกสร้างขึ้นตอนระบุวัตถุ cJSON
**ผลเสียหากละเลย (Memory Leak):**  
เนื่องจากฟังก์ชัน `telemetry_task` ทำงานเป็นวนรอบ (Loop) ทุกๆ 4 วินาที หากไม่มีการคืนหน่วยความจำ หน่วยความจำสะสม (Heap Memory) ของ ESP32 จะถูกใช้ไปเรื่อยๆ จนกระทั่งเกิดปัญหา **Heap Exhaustion / Out of Memory** ส่งผลทำให้บอร์ดเกิดอาการแฮงก์ หรือเกิดระบบล่มและทำการรีเซ็ตตัวเอง (Kernel Panic / Crash Breakpoint) ในที่สุด
