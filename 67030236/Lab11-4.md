## 5. คำถามท้ายการทดลอง (Post-Lab Questions)
1. ในสถาปัตยกรรม ESP RainMaker กระบวนการ **Assisted Claiming** ช่วยแก้ปัญหาเรื่องการติดตั้งใบรับรองความปลอดภัย (Security Certificates) บนอุปกรณ์ในขั้นตอนพัฒนาต้นแบบได้อย่างไร?
```text
Assisted Claiming ช่วยให้นักพัฒนาไม่ต้องติดตั้งใบรับรองลงบนบอร์ดด้วยตนเองล่วงหน้า โดยอาศัยแอปพลิเคชัน RainMaker บนสมาร์ตโฟนเป็นตัวกลางเชื่อมต่อ Cloud เพื่อขอรับ Certificate ประจำตัวอุปกรณ์แล้วส่งผ่าน BLE หรือ SoftAP ไปบันทึกลงหน่วยความจำ NVS ของ ESP32 อัตโนมัติระหว่างกระบวนการ Provisioning
```
2. เพราะเหตุใดฟังก์ชัน `write_cb` จึงต้องเรียกคำสั่ง `esp_rmaker_param_update_and_report()` ทุกครั้งที่มีการเปลี่ยนแปลงค่าพารามิเตอร์?
```text
เพื่ออัปเดตค่าพารามิเตอร์ใหม่ในหน่วยความจำของอุปกรณ์ และส่งสถานะล่าสุดกลับไปซิงก์กับ Cloud ของ RainMaker ทันที ทำให้หน้าจอแอปพลิเคชันมือถือแสดงผลสถานะจริงของอุปกรณ์ได้อย่างถูกต้อง
```
3. เปรียบเทียบความแตกต่างระหว่างการพัฒนาอุปกรณ์ IoT ด้วย **Plain MQTT บน Mosquitto เอง (ในแล็บ 11.2)** กับการใช้ **ESP RainMaker SDK (ในแล็บ 11.4)** ในแง่ของความพยายามในการพัฒนา (Development Effort), ความปลอดภัย (Security), และการขยายระบบ (Scalability)

| ปัจจัยเปรียบเทียบ (Aspect) | Plain MQTT บน Mosquitto (Lab 11.2) | ESP RainMaker SDK (Lab 11.4) |
| :--- | :--- | :--- |
| **🛠️ ความพยายามในการพัฒนา<br>(Development Effort)** | **สูงมาก (High Effort)**<br>• ต้องออกแบบโครงสร้าง Topic & JSON Schema เอง<br>• ต้องเขียนระบบ Wi-Fi Provisioning เอง<br>• ต้องพัฒนา Mobile App / Dashboard เองทั้งหมด | **ต่ำมาก (Turnkey Solution)**<br>• มี API จัดการ Device Data Model (Params) ให้ในตัว<br>• มีระบบ Wi-Fi Provisioning ผ่าน BLE/SoftAP ในตัว<br>• มี Mobile App มาตรฐาน (iOS/Android) ใช้งานได้ทันที |
| **🔒 ความปลอดภัย<br>(Security)** | **ขึ้นอยู่กับการตั้งค่า (Manual Configuration)**<br>• ต้องสร้าง CA, Server/Client Certificates และคอนฟิก mTLS เอง<br>• เสี่ยงต่อการรั่วไหลหากไม่มีการทำ Flash Encryption จัดเก็บ Private Key | **ระดับองค์กร (Enterprise Grade)**<br>• บังคับใช้ mTLS ผ่าน AWS IoT Core อัตโนมัติ<br>• มีระบบ **Assisted Claiming** ติดตั้ง Certificate ให้อัตโนมัติ<br>• ผูกสิทธิ์การเข้าถึงอุปกรณ์กับระบบ User Account (OAuth) |
| **📈 การขยายระบบ<br>(Scalability)** | **จำกัด (Limited)**<br>• ข้อจำกัดขึ้นอยู่กับ Spec และการคอนฟิก Broker เดี่ยว<br>• ต้องดูแลรักษา Infrastructure, Server Scaling และ Clustering เอง | **ไร้ขีดจำกัด (Highly Scalable)**<br>• ทำงานบนโครงสร้างพื้นฐาน AWS Serverless & AWS IoT Core<br>• รองรับการเชื่อมต่ออุปกรณ์ระดับหมื่นถึงล้านเครื่องได้ทันที |
| **💡 สรุปการประยุกต์ใช้<br>(Best Use Case)** | เหมาะสำหรับระบบปิดภายในองค์กร (Local / On-premise), ระบบที่ไม่ต้องการพึ่งพาคลาวด์ภายนอก หรือต้องการควบคุม Infrastructure ทั้งหมดเอง | เหมาะสำหรับผลิตภัณฑ์ IoT เชิงพาณิชย์ (Smart Home / Consumer IoT) ที่ต้องการเปิดตัวเร็ว (Fast Time-to-Market) และเน้น Scale อุปกรณ์จำนวนมาก |
4. อธิบายขั้นตอนที่ทำให้ ESP RainMaker สามารถเชื่อมโยงการทำงานร่วมกับระบบสั่งงานด้วยเสียงของ **Google Home** หรือ **Amazon Alexa** ได้โดยไม่ต้องเขียนโค้ดเพิ่มเติมบนตัวบอร์ด ESP32
```text
เพราะ RainMaker จัดการเชื่อมต่อแบบ Cloud-to-Cloud ให้แล้ว ตัวบอร์ด ESP32 จึงแค่รับค่าพารามิเตอร์ผ่าน MQTT เดิมตามปกติ โดยที่ฝั่งคลาวด์เป็นผู้แปลงคำสั่งเสียงจาก Google/Alexa ให้เอง
```
