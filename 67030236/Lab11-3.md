## 5. คำถามท้ายการทดลอง (Post-Lab Questions)
1. เพราะเหตุใดในคำสั่งสร้าง Server CSR ค่า **Common Name (CN)** จึงต้องระบุเป็น IP Address หรือ Hostname ของ Broker ให้ตรงกันพอดี? หากระบุเป็นชื่ออื่นจะเกิดข้อผิดพลาดใดขึ้น?
```text
เพราะฝั่งไคลเอนต์ใช้ค่า CN ในการตรวจสอบเพื่อยืนยันตัวตนของเซิร์ฟเวอร์ว่าตรงกับปลายทางที่กำลังเชื่อมต่อจริงเพื่อป้องกันการปลอมแปลง (MitM); หากระบุไม่ตรงกัน ขั้นตอนการทำ TLS Handshake จะล้มเหลวทันทีเนื่องจากเกิดข้อผิดพลาด Hostname/CN Verification Mismatch
```
2. การยืนยันตัวตนแบบ **Mutual Authentication (mTLS)** แตกต่างจากการใช้ **HTTPS** ทั่วไปบนเว็บเบราว์เซอร์อย่างไรในประเด็นเรื่องใบรับรองฝั่ง Client?
```text
HTTPS ทั่วไปจะตรวจสอบใบรับรองเฉพาะฝั่งเซิร์ฟเวอร์เท่านั้น (One-way TLS) โดยฝั่ง Client ไม่ต้องมีใบรับรอง ในขณะที่ mTLS บังคับให้ฝั่ง Client ต้องส่งใบรับรองดิจิทัลและใช้ Private Key ของตนเองเพื่อยืนยันตัวตนกลับไปยังเซิร์ฟเวอร์ด้วย
```
3. หากมีผู้ไม่หวังดีขโมยไฟล์เฟิร์มแวร์ไบนารี (`.bin`) ของบอร์ด ESP32 ไปได้ เขาจะสามารถกู้คืนไฟล์ `client.key` ได้หรือไม่ และในระบบ IoT เชิงพาณิชย์เรามีฮาร์ดแวร์ความปลอดภัยใด (เช่น ESP32 Secure Boot / Flash Encryption / Digital Signature Peripheral) มาช่วยแก้ไขปัญหานี้?
```text
หากไม่มีการป้องกัน ผู้โจมตีสามารถสกัด client.key ออกมาได้โดยง่าย แต่สามารถแก้ไขได้ด้วยการเปิดใช้ Flash Encryption ร่วมกับ Secure Boot เพื่อเข้ารหัสข้อมูลบนชิปและป้องกันการรันโค้ดดัดแปลง หรือใช้ฮาร์ดแวร์ Digital Signature Peripheral (DS) เพื่อเซ็นข้อมูลยืนยันตัวตน mTLS โดยที่ Private Key ถูกล็อกไว้ใน eFuse และไม่มีวันถูกดึงออกมาเป็น Plaintext ได้เลย
```
