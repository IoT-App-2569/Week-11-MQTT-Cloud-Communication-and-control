## ผลการทดลองและการบันทึกภาพหน้าจอ

### 1. ภาพหน้าจอการทดสอบ mTLS สำเร็จผ่าน Mosquitto CLI (Sub/Pub พร้อม Certificate)
* แสดงผลลัพธ์ในหน้าต่าง Subscriber ที่ได้รับข้อความ `"Hello Secure World!"` พร้อม Log ฝั่ง Mosquitto Broker ที่แสดงการ Handshake และยืนยันใบรับรอง Client

---

### 2. ภาพหน้าจอการทดสอบปฏิเสธ Client ที่ไม่ได้รับอนุญาต (Unauthorized Client Attack)
* แสดงผลลัพธ์เมื่อส่ง Publish โดยไม่แนบ Client Certificate แล้ว Broker แจ้งปฏิเสธการเชื่อมต่อ `Connection refused: Not authorised` หรือ `peer did not return a certificate`

![การทดสอบปฏิเสธ Client ที่ไม่ได้รับอนุญาต](image-6.png)

---

### 3. ภาพหน้าจอ ESP32 เชื่อมต่อ MQTTS แบบ mTLS สำเร็จ
* แสดงผลหน้าจอ Serial Monitor ของ ESP32 ขณะทำ TLS Handshake สำเร็จ และ Broker Log แสดงการยืนยันใบรับรองของ ESP32 (`Peer certificate verified: ... CN=esp32-secure-node`)

## คำถามท้ายการทดลอง (Post-Lab Questions)

### ข้อ 1: เพราะเหตุใดในคำสั่งสร้าง Server CSR ค่า Common Name (CN) จึงต้องระบุเป็น IP Address หรือ Hostname ของ Broker ให้ตรงกันพอดี? หากระบุเป็นชื่ออื่นจะเกิดข้อผิดพลาดใดขึ้น?
* **คำตอบ:**
  1. **เหตุผลที่ต้องระบุให้ตรงกันพอดี:**
     * ในมาตรฐานความปลอดภัย TLS/SSL ฝั่ง Client (เช่น ESP32 หรือ Mosquitto CLI) เมื่อเชื่อมต่อไปยัง Server จะต้องทำการตรวจสอบความถูกต้องของ Server Certificate ว่าเป็นเครื่องเซิร์ฟเวอร์เป้าหมายตัวจริงหรือไม่ โดยจะนำชื่อ Hostname หรือหมายเลข IP Address ใน URL ที่ใช้เชื่อมต่อ ไปเปรียบเทียบกับฟิลด์ **Common Name (CN)** หรือ **Subject Alternative Name (SAN)** ที่ระบุอยู่ในใบรับรองของ Server
     * การระบุ CN ให้ตรงกับ IP จริง (เช่น `192.168.1.37`) เป็นการยืนยันอัตลักษณ์ของเซิร์ฟเวอร์ เพื่อป้องกันการถูกดักโจมตีแบบสวมรอยหรือคนกลาง (Man-in-the-Middle Attack: MitM)
  2. **ข้อผิดพลาดที่จะเกิดขึ้นหากระบุเป็นชื่ออื่น:**
     * ในขั้นตอน TLS Handshake ตัว Client จะตรวจพบว่า Hostname/IP ที่กำลังเชื่อมต่อ ไม่ตรงกับ CN ในใบรับรอง เกิดข้อผิดพลาด **Hostname Mismatch / Certificate Verification Failed**
     * ตัว Client (รวมถึง ESP32 ในส่วนของ MbedTLS) จะตัดการเชื่อมต่อทันที และแจ้งข้อผิดพลาดระดับ Transport (เช่น `ESP_ERR_MBEDTLS_SSL_HANDSHAKE_FAILED` หรือ `X509 - Certificate verification failed, e.g. CRL, name mismatch`) ทำให้ไม่สามารถสร้างการเชื่อมต่อ MQTTS ได้

### ข้อ 2: การยืนยันตัวตนแบบ Mutual Authentication (mTLS) แตกต่างจากการใช้ HTTPS ทั่วไปบนเว็บเบราว์เซอร์อย่างไรในประเด็นเรื่องใบรับรองฝั่ง Client?
* **คำตอบ:**
  1. **HTTPS ทั่วไปบนเว็บเบราว์เซอร์ (One-Way TLS / Server Authentication):**
     * มีเพียง **Server ฝ่ายเดียวเท่านั้น** ที่ต้องมีและส่งใบรับรองดิจิทัล (Server Certificate) ให้เบราว์เซอร์ตรวจสอบ เพื่อยืนยันว่าเว็บไซต์นั้นเป็นของจริง
     * ฝั่ง **Client (ผู้ใช้งาน / เบราว์เซอร์) ไม่จำเป็นต้องมีใบรับรองดิจิทัล** แต่อย่างใด การยืนยันตัวตนของผู้ใช้จะไปทำในระดับแอปพลิเคชัน (Application Layer) แทน เช่น การกรอก Username, Password, Token, หรือ OTP
  2. **Mutual Authentication (mTLS / Two-Way Authentication):**
     * **ทั้งสองฝ่ายต้องมีและแลกเปลี่ยนใบรับรองดิจิทัลซึ่งกันและกัน (Mutual Verification)**
     * ในขั้นตอน TLS Handshake นอกจาก Client จะตรวจ Server Certificate แล้ว **Server จะส่งคำขอ `Certificate Request` สั่งให้ Client ต้องส่ง Client Certificate และพิสูจน์ความเป็นเจ้าของด้วย Client Private Key กลับมาด้วย**
     * หาก Client ไม่มีใบรับรอง หรือใบรับรองไม่ได้ถูกลงนามรับรอง (Sign) โดย Root CA ที่ Broker เชื่อถือ Server จะปฏิเสธการเชื่อมต่อและตัดสายทันทีตั้งแต่ระดับ Cryptographic Handshake ก่อนจะเริ่มส่งข้อมูล MQTT ใดๆ
     * เหมาะอย่างยิ่งสำหรับระบบ IoT ระดับอุตสาหกรรม/องค์กร เพราะเป็นการยืนยันสิทธิ์ของอุปกรณ์ฮาร์ดแวร์โดยตรง (Device Identity) ป้องกันการปลอมแปลงโหนดในระบบเครือข่าย

### ข้อ 3: หากมีผู้ไม่หวังดีขโมยไฟล์เฟิร์มแวร์ไบนารี (`.bin`) ของบอร์ด ESP32 ไปได้ เขาจะสามารถกู้คืนไฟล์ `client.key` ได้หรือไม่ และในระบบ IoT เชิงพาณิชย์เรามีฮาร์ดแวร์ความปลอดภัยใด (เช่น ESP32 Secure Boot / Flash Encryption / Digital Signature Peripheral) มาช่วยแก้ไขปัญหานี้?
* **คำตอบ:**
  1. **การกู้คืนไฟล์ `client.key` จากไฟล์ไบนารี:**
     * **สามารถกู้คืนได้ง่ายมาก** หากไม่มีระบบป้องกันเสริม เพราะคำสั่ง `EMBED_TXTFILES` ของ CMake จะทำการฝังเนื้อหาไฟล์ `client.key` (RSA Private Key ในรูปแบบข้อความ ASCII PEM) ลงไปใน Flash Binary แบบดิบๆ (Plaintext) 
     * ผู้ไม่หวังดีเพียงแค่ใช้คำสั่งตรวจสอบข้อความธรรมดา เช่น `strings firmware.bin` หรือใช้โปรแกรม Hex Editor ก็จะพบข้อความส่วนหัว `-----BEGIN RSA PRIVATE KEY-----` และสามารถคัดลอกกุญแจส่วนตัวออกมาสวมรอยเป็นอุปกรณ์ตัวนั้นได้อย่างสมบูรณ์
  2. **ฮาร์ดแวร์ความปลอดภัยของ ESP32 ที่นำมาช่วยแก้ไขปัญหาในเชิงพาณิชย์:**
     * **ESP32 Flash Encryption:** เป็นกลไกฮาร์ดแวร์ที่เข้ารหัสข้อมูลใน Flash Memory ทั้งหมดด้วยกุญแจ AES-256 (ซึ่งถูกฝังอยู่ใน eFuse ของชิปและอ่านจากภายนอกไม่ได้) ทำให้ข้อมูลที่ถูกดูดออกจากชิปหรือไฟล์ไบนารีที่อยู่นอกตัวชิปกลายเป็นข้อมูลที่เข้ารหัส อ่านไม่รู้เรื่อง และไม่สามารถดึง `client.key` ออกมาได้
     * **ESP32 Secure Boot:** ตรวจสอบลายมือชื่อดิจิทัล (Digital Signature) ของเฟิร์มแวร์ทุกครั้งที่บอร์ดเริ่มทำงาน เพื่อให้มั่นใจว่าจะรันเฉพาะเฟิร์มแวร์ของแท้ที่ผู้ผลิตลงนามรับรองไว้เท่านั้น ป้องกันไม่ให้แฮกเกอร์แอบแฟลชเฟิร์มแวร์ดัดแปลงเพื่อมาอ่านค่า Key
     * **Digital Signature Peripheral (DS Peripheral):** เป็นโมดูลฮาร์ดแวร์เฉพาะในชิปรุ่นใหม่ (เช่น ESP32-S2, S3, C3) ที่นำ Private Key ไปเก็บไว้ใน eFuse ซึ่งถูกเข้ารหัสด้วยฮาร์ดแวร์ (HMAC Key) ซอฟต์แวร์จะไม่สามารถเข้าถึงเนื้อ Private Key โดยตรงได้ แต่เมื่อต้องการทำ TLS Handshake จะสั่งให้ฮาร์ดแวร์ DS นี้เป็นผู้คำนวณถอด/เข้ารหัส Signature ให้โดยตรง ทำให้แม้เฟิร์มแวร์จะถูกอ่านไบนารีออกไป ก็ไม่มีไฟล์กุญแจส่วนตัวหลุดออกไปอย่างแน่นอน
