# ใบงานการทดลองที่ 11.3
## 5. คำถามท้ายการทดลอง (Post-Lab Questions)
1. เพราะเหตุใดในคำสั่งสร้าง Server CSR ค่า **Common Name (CN)** จึงต้องระบุเป็น IP Address หรือ Hostname ของ Broker ให้ตรงกันพอดี? หากระบุเป็นชื่ออื่นจะเกิดข้อผิดพลาดใดขึ้น?

```text
**เพราะ Client ใช้ค่า CN ตรวจสอบว่าใบรับรองที่ได้รับเป็นของเครื่องที่ตนตั้งใจเชื่อมต่อจริง หากไม่ตรงกันจะเกิด Hostname Mismatch และ TLS Handshake ล้มเหลว**
 
- ระหว่าง TLS Handshake Client จะตรวจ 2 เรื่อง คือ ใบรับรองถูกลงนามโดย CA ที่เชื่อถือหรือไม่ และชื่อในใบรับรองตรงกับที่อยู่ใน URI ที่เชื่อมต่อ (เช่น `192.168.1.100`) หรือไม่ ขั้นตอนหลังนี้เรียกว่า Hostname Verification
- ขั้นตอนนี้ป้องกันการโจมตีแบบ Man-in-the-Middle เพราะแม้ผู้โจมตีจะมีใบรับรองที่ลงนามโดย CA เดียวกัน ก็ไม่สามารถปลอมตัวเป็น Broker ที่มี IP หรือชื่ออื่นได้
- หากระบุ CN เป็นชื่ออื่น ฝั่ง ESP32 (mbedTLS) จะปฏิเสธใบรับรองด้วยข้อผิดพลาด CN Mismatch และเกิด `MQTT_EVENT_ERROR` ส่วน `mosquitto_sub` หรือ `mosquitto_pub` จะแจ้ง TLS Error ว่าตรวจสอบใบรับรองไม่ผ่าน (certificate verify failed)
- การปิดการตรวจสอบ เช่น ใช้แฟล็ก `--insecure` หรือตั้งค่า `skip_cert_common_name_check` ทำให้เชื่อมต่อได้ แต่จะสูญเสียการป้องกัน Man-in-the-Middle จึงไม่ควรใช้ในระบบจริง
```

2. การยืนยันตัวตนแบบ **Mutual Authentication (mTLS)** แตกต่างจากการใช้ **HTTPS** ทั่วไปบนเว็บเบราว์เซอร์อย่างไรในประเด็นเรื่องใบรับรองฝั่ง Client?

```text
**HTTPS ทั่วไปยืนยันตัวตนทางเดียวโดยใช้ใบรับรองฝั่ง Server เท่านั้น ส่วน mTLS ยืนยันตัวตนทั้งสองฝ่าย โดย Client ต้องมีใบรับรองของตัวเองด้วย**
 
- **HTTPS ทั่วไป (One-way TLS)** มีเพียง Server ที่ส่งใบรับรองมาให้เบราว์เซอร์ตรวจกับ Public CA ที่เชื่อถือ ฝั่งเบราว์เซอร์ไม่มีใบรับรอง ผู้ใช้จึงต้องยืนยันตัวตนภายหลังในระดับแอปพลิเคชัน เช่น Username/Password, Cookie หรือ OTP
- **mTLS (Two-way TLS)** Server ส่งคำขอ `CertificateRequest` ระหว่าง Handshake Client ต้องส่งใบรับรอง (`client.crt`) และพิสูจน์ว่าถือกุญแจส่วนตัวจริงด้วยการลงนาม (`CertificateVerify`) โดยใช้ `client.key`
- Broker ตรวจใบรับรองของ Client กับ `ca.crt` ตามการตั้งค่า `require_certificate true` หาก Client ไม่มีใบรับรองหรือใบรับรองไม่ถูกต้อง จะถูกปฏิเสธตั้งแต่ระดับ TLS ก่อนจะส่งแพ็กเก็ต MQTT `CONNECT` ได้ ดังที่เห็นในการทดลอง `peer did not return a certificate`
- mTLS เหมาะกับระบบ IoT เพราะอุปกรณ์ไม่มีผู้ใช้คอยกรอกรหัสผ่าน แต่ละอุปกรณ์มีตัวตนเฉพาะ (เช่น `CN=esp32-secure-node`) และสามารถเพิกถอนใบรับรองของอุปกรณ์ที่ถูกขโมยได้ทีละตัว
```


3. หากมีผู้ไม่หวังดีขโมยไฟล์เฟิร์มแวร์ไบนารี (`.bin`) ของบอร์ด ESP32 ไปได้ เขาจะสามารถกู้คืนไฟล์ `client.key` ได้หรือไม่ และในระบบ IoT เชิงพาณิชย์เรามีฮาร์ดแวร์ความปลอดภัยใด (เช่น ESP32 Secure Boot / Flash Encryption / Digital Signature Peripheral) มาช่วยแก้ไขปัญหานี้?

```text
**กู้คืนได้ เพราะ `EMBED_TXTFILES` ฝังไฟล์ไว้ในเฟิร์มแวร์แบบข้อความธรรมดา (Plaintext PEM) โดยไม่มีการเข้ารหัส**
 
- เพียงใช้คำสั่งอย่าง `strings` ค้นหาข้อความ `-----BEGIN PRIVATE KEY-----` ในไฟล์ `.bin` ก็คัดลอกกุญแจออกมาได้ทันที หรืออ่านจากบอร์ดจริงโดยตรงด้วย `esptool read_flash` ผู้โจมตีจึงสามารถปลอมตัวเป็นอุปกรณ์และเชื่อมต่อ Broker ได้
- **Flash Encryption** เข้ารหัสข้อมูลทั้งหมดใน Flash ด้วย AES โดยใช้กุญแจที่เก็บใน eFuse ซึ่งซอฟต์แวร์อ่านออกมาไม่ได้ ข้อมูลที่ Dump ออกจากชิปจึงอ่านไม่ออก
- **Secure Boot** ตรวจลายเซ็นดิจิทัลของ Bootloader และเฟิร์มแวร์ก่อนรันทุกครั้ง ป้องกันผู้โจมตีแฟลชเฟิร์มแวร์ดัดแปลงเพื่อดึงกุญแจออกมา จึงควรใช้คู่กับ Flash Encryption เสมอ
- **Digital Signature (DS) Peripheral** (มีใน ESP32-S2/S3/C3/C6 แต่ไม่มีใน ESP32 รุ่นแรก) เก็บกุญแจส่วนตัวในรูปที่เข้ารหัสด้วยกุญแจใน eFuse และลงนามระหว่าง TLS Handshake ด้วยฮาร์ดแวร์ กุญแจจึงไม่เคยปรากฏเป็น Plaintext ในหน่วยความจำที่ซอฟต์แวร์เข้าถึงได้
```
