# ใบงานการทดลองที่ 11.4
## 5. คำถามท้ายการทดลอง (Post-Lab Questions)
1. ในสถาปัตยกรรม ESP RainMaker กระบวนการ **Assisted Claiming** ช่วยแก้ปัญหาเรื่องการติดตั้งใบรับรองความปลอดภัย (Security Certificates) บนอุปกรณ์ในขั้นตอนพัฒนาต้นแบบได้อย่างไร?

```text
**Assisted Claiming ให้แอปบนสมาร์ตโฟนเป็นตัวกลางขอใบรับรองจากคลาวด์มาให้อุปกรณ์โดยอัตโนมัติ ผู้พัฒนาจึงไม่ต้องสร้างและฝังใบรับรองเองทีละเครื่อง**
 
- ในแล็บ 11.3 ต้องใช้ OpenSSL สร้าง CA, ออกใบรับรอง Client แล้วฝังลงเฟิร์มแวร์ด้วย `EMBED_TXTFILES` เอง ซึ่งยุ่งยาก และเสี่ยงที่ทุกบอร์ดจะใช้กุญแจชุดเดียวกัน
- ใน Assisted Claiming บอร์ด ESP32 สร้างคู่กุญแจและคำร้องขอใบรับรอง (CSR) ขึ้นเองภายในชิป แล้วส่ง CSR ผ่าน BLE ไปยังแอป แอปที่ล็อกอินบัญชีผู้ใช้อยู่จะส่งต่อให้ RainMaker Cloud ลงนาม และส่งใบรับรองกลับมาให้บอร์ดเก็บไว้ใน NVS
- กุญแจส่วนตัวไม่เคยออกจากตัวบอร์ด และแต่ละบอร์ดได้ใบรับรองเฉพาะของตัวเอง ทำให้ปลอดภัยกว่าการฝังไฟล์กุญแจไว้ในเฟิร์มแวร์
- บอร์ดยังไม่จำเป็นต้องต่ออินเทอร์เน็ตในขั้นตอนนี้ เพราะใช้การเชื่อมต่ออินเทอร์เน็ตและการยืนยันตัวตนของแอปบนสมาร์ตโฟนแทน และทำพร้อมกับขั้นตอน BLE Provisioning ได้ในครั้งเดียว
```

2. เพราะเหตุใดฟังก์ชัน `write_cb` จึงต้องเรียกคำสั่ง `esp_rmaker_param_update_and_report()` ทุกครั้งที่มีการเปลี่ยนแปลงค่าพารามิเตอร์?

```text
**เพื่ออัปเดตค่าพารามิเตอร์ภายในอุปกรณ์และรายงานสถานะจริงกลับไปยังคลาวด์ ให้ทุกฝั่งเห็นสถานะเดียวกัน**
 
- `write_cb` เพียงแค่รับคำสั่งและควบคุมฮาร์ดแวร์ (เช่น `gpio_set_level`) แต่ RainMaker ไม่ได้อัปเดตค่าพารามิเตอร์ในโมเดลข้อมูลของอุปกรณ์ให้อัตโนมัติ
- คำสั่งนี้ทำหน้าที่ยืนยันว่าอุปกรณ์รับคำสั่งและเปลี่ยนสถานะสำเร็จแล้ว (Closed-loop Feedback) เหมือนการส่ง `iot/node01/state/led` กลับในแล็บ 11.2
- หากไม่รายงานกลับ สวิตช์หรือสไลเดอร์บนแอปอาจเด้งกลับค่าเดิมหรือแสดงสถานะไม่ตรงกับหลอดไฟจริง และสมาร์ตโฟนเครื่องอื่นที่ดูอุปกรณ์เดียวกันจะไม่เห็นการเปลี่ยนแปลง
- บริการอื่นที่อ่านสถานะจากคลาวด์ เช่น Schedule, Google Home หรือ Alexa จะได้ข้อมูลผิด เพราะคลาวด์ยังเก็บค่าเดิมไว้

```

3. เปรียบเทียบความแตกต่างระหว่างการพัฒนาอุปกรณ์ IoT ด้วย **Plain MQTT บน Mosquitto เอง (ในแล็บ 11.2)** กับการใช้ **ESP RainMaker SDK (ในแล็บ 11.4)** ในแง่ของความพยายามในการพัฒนา (Development Effort), ความปลอดภัย (Security), และการขยายระบบ (Scalability)

```text
**Plain MQTT ยืดหยุ่นและควบคุมได้ทุกส่วน แต่ต้องสร้างเองทั้งหมด ส่วน RainMaker มีระบบสำเร็จรูปครบ แต่ผูกติดกับแพลตฟอร์มของ Espressif**
 
- **Development Effort** แล็บ 11.2 ต้องฝังชื่อและรหัส Wi-Fi ในโค้ด ติดตั้ง Broker ออกแบบ Topic และรูปแบบ JSON เขียนโค้ดแยกคำสั่งเอง และยังไม่มีแอปสำหรับผู้ใช้ ส่วน RainMaker มี BLE Provisioning, แอปมือถือ, Schedule, Time Sync และ OTA ให้พร้อมใช้ เพียงประกาศ Device และ Parameter
- **Security** แล็บ 11.2 เชื่อมต่อแบบ `mqtt://` พอร์ต 1883 ไม่มีการเข้ารหัส และเปิด `allow_anonymous true` ใครก็ Publish คำสั่งได้ หากต้องการปลอดภัยต้องตั้งค่า TLS/mTLS เองเหมือนแล็บ 11.3 ส่วน RainMaker ใช้ mTLS พร้อมใบรับรองเฉพาะแต่ละอุปกรณ์ และผูกอุปกรณ์กับบัญชีผู้ใช้ที่ยืนยันตัวตนแล้วโดยอัตโนมัติ
- **Scalability** Mosquitto ที่ติดตั้งเองบนเครื่องเดียวรองรับได้จำกัด หากต้องการรองรับอุปกรณ์จำนวนมาก ต้องจัดการ Server, Cluster, ฐานข้อมูล และการสำรองข้อมูลเอง ส่วน RainMaker ทำงานบนบริการคลาวด์ของ AWS แบบ Serverless จึงขยายรองรับอุปกรณ์และผู้ใช้จำนวนมากได้โดยไม่ต้องดูแล Server
- **ข้อแลกเปลี่ยน** RainMaker ต้องพึ่งพาอินเทอร์เน็ตและแพลตฟอร์มของ Espressif ปรับแต่งโปรโตคอลได้น้อยกว่า และการใช้งานเชิงพาณิชย์ต้องใช้ Private Deployment ซึ่งมีค่าใช้จ่าย ส่วน Plain MQTT ทำงานในวงแลนได้แม้ไม่มีอินเทอร์เน็ต และใช้กับอุปกรณ์ทุกยี่ห้อได้
```

| ประเด็น | Plain MQTT (แล็บ 11.2) | ESP RainMaker (แล็บ 11.4) |
| :--- | :--- | :--- |
| Development Effort | สูง ต้องสร้างเองทุกส่วน | ต่ำ มีระบบสำเร็จรูป |
| Security | ไม่เข้ารหัส ต้องตั้งค่าเอง | mTLS และผูกบัญชีผู้ใช้ในตัว |
| Scalability | จำกัด ต้องดูแล Server เอง | ขยายอัตโนมัติบนคลาวด์ |
| ความยืดหยุ่น | สูง ไม่ผูกกับผู้ให้บริการ | จำกัดตามแพลตฟอร์ม |

4. อธิบายขั้นตอนที่ทำให้ ESP RainMaker สามารถเชื่อมโยงการทำงานร่วมกับระบบสั่งงานด้วยเสียงของ **Google Home** หรือ **Amazon Alexa** ได้โดยไม่ต้องเขียนโค้ดเพิ่มเติมบนตัวบอร์ด ESP32

```text
**การเชื่อมต่อเกิดขึ้นระหว่างคลาวด์กับคลาวด์ (Cloud-to-Cloud) ทั้งหมด บอร์ด ESP32 ยังคงสื่อสารกับ RainMaker Cloud เพียงช่องทางเดียวเหมือนเดิม**
 
- **ใช้ประเภทมาตรฐาน** โค้ดสร้างอุปกรณ์ด้วย `esp_rmaker_lightbulb_device_create()` และพารามิเตอร์มาตรฐาน Power และ Brightness คลาวด์จึงรู้ว่าเป็นหลอดไฟ และแปลงเป็นความสามารถของแต่ละระบบได้ เช่น OnOff และ Brightness ของ Google หรือ PowerController และ BrightnessController ของ Alexa
- **เชื่อมบัญชี (Account Linking)** ผู้ใช้เปิดแอป Google Home หรือ Alexa แล้วเพิ่มบริการ ESP RainMaker และล็อกอินด้วยบัญชี RainMaker ผ่าน OAuth ทำให้ Google หรือ Amazon ได้รับสิทธิ์เข้าถึงอุปกรณ์ในบัญชีนั้น
- **ค้นหาอุปกรณ์ (Discovery)** Google หรือ Amazon ขอรายการอุปกรณ์จาก RainMaker Cloud แล้วแสดง "Living Room Light" ขึ้นในแอปของตน
- **สั่งงานด้วยเสียง** เมื่อผู้ใช้พูดคำสั่ง เช่น "Turn on Living Room Light" คลาวด์ของ Google หรือ Amazon ส่งคำสั่งต่อมายัง RainMaker Cloud ซึ่งส่งต่อผ่าน MQTT มายังบอร์ด และเรียก `write_cb` เหมือนการกดจากแอป RainMaker จากนั้นสถานะที่รายงานด้วย `esp_rmaker_param_update_and_report()` จะถูกส่งกลับไปให้ระบบสั่งงานด้วยเสียงทราบ

```
