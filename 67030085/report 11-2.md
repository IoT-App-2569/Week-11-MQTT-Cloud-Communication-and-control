## คำถามท้ายการทดลอง (Post-Lab Questions)

### ข้อ 1: เพราะเหตุใดเราจึงต้องส่งข้อความสถานะ `iot/node01/status = "online"` ด้วยแฟล็ก `retain = 1` ควบคู่กับการตั้งค่า Last Will and Testament (LWT) ว่า `"offline"`?
* **คำตอบ:** เพื่อสร้างระบบ **Device State Synchronization (Online/Offline Presence Pattern)** ที่สมบูรณ์และเชื่อถือได้
  1. **การส่ง `"online"` ด้วยแฟล็ก `retain = 1` (State Persistence):**
     * เมื่อบอร์ด ESP32 เริ่มทำงานและเชื่อมต่อกับ Broker สำเร็จในเหตุการณ์ `MQTT_EVENT_CONNECTED` บอร์ดจะส่งสถานะ `"online"` เพียงครั้งเดียว
     * การตั้ง `retain = 1` สั่งให้ Broker บันทึกข้อความนี้ไว้ในหน่วยความจำถาวร เมื่อมีแดชบอร์ดหรือผู้ใช้งานรายใหม่ (New Subscriber) เพิ่งเปิดแอปพลิเคชันขึ้นมา จะได้รับสถานะล่าสุดทันทีโดยไม่ต้องรอรอบการส่งถัดไป ช่วยแก้ปัญหาหน้าจอแดชบอร์ดว่างเปล่า (Blank Dashboard)
  2. **การตั้ง LWT เป็น `"offline"` พร้อม `retain = 1` (Abnormal Disconnect Handler):**
     * ในกรณีที่บอร์ดเกิดเหตุฉุกเฉิน เช่น ไฟดับ, บอร์ดค้าง (Crash), สัญญาณเครือข่ายหลุด หรือหมดเวลา Keep-Alive (60 วินาที) โดยไม่ได้รับแพ็กเก็ต `DISCONNECT`
     * Broker จะทำหน้าที่แทนอุปกรณ์โดยนำข้อความพินัยกรรม `"offline"` ที่ตั้ง `retain = 1` ไว้ ไป **เขียนทับ (Atomic Overwrite)** สถานะ `"online"` เดิมบนหัวข้อ `iot/node01/status` พร้อมแจ้งเตือนไปยังผู้ติดตามทันที
  3. **สรุป:** การทำงานผสานกันระหว่าง Retain Message และ LWT ช่วยให้ระบบทราบสถานะจริงของอุปกรณ์ (Availability) ได้อย่างแม่นยำตลอดเวลา ทั้งสำหรับผู้ที่กำลังเฝ้าดูอยู่และผู้ที่เพิ่งเชื่อมต่อเข้ามาใหม่

### ข้อ 2: หากเครือข่าย Wi-Fi หลุดชั่วคราว คอมโพเนนต์ `esp-mqtt` มีพฤติกรรมการจัดการอย่างไร และเมื่อสัญญาณกลับมา โค้ดจำเป็นต้องเรียกฟังก์ชันเชื่อมต่อใหม่ด้วยตนเองหรือไม่?
* **คำตอบ:**
  1. **พฤติกรรมของคอมโพเนนต์ `esp-mqtt` เมื่อ Wi-Fi หลุด:**
     * เมื่อการเชื่อมต่อทางกายภาพหรือ Socket ขาดหาย เลเยอร์ Transport จะตรวจพบข้อผิดพลาด และส่งเหตุการณ์ **`MQTT_EVENT_DISCONNECTED`** เข้าสู่ฟังก์ชัน `mqtt_event_handler`
     * ภายในคอมโพเนนต์ `esp-mqtt` มี FreeRTOS Task ทำงานอยู่เบื้องหลังพร้อมระบบ **Auto-Reconnect** โดยจะตั้งเวลาหน่วงตามค่า `reconnect_timeout_ms` (ค่าเริ่มต้น 10 วินาที) และพยายามสร้างการเชื่อมต่อไปยัง Broker ใหม่อย่างต่อเนื่องโดยอัตโนมัติ
  2. **เมื่อสัญญาณกลับมา จำเป็นต้องเรียกคำสั่งเชื่อมต่อใหม่ด้วยตนเองหรือไม่?**
     * **ในฝั่งของ MQTT: ไม่จำเป็นต้องเรียกฟังก์ชันเชื่อมต่อใหม่ด้วยตนเอง** (ไม่ต้องสั่ง `esp_mqtt_client_reconnect()` หรือ `esp_mqtt_client_start()` ซ้ำ) เมื่อระดับเน็ตเวิร์กพร้อมใช้งาน `esp-mqtt` จะสร้าง TCP Socket ใหม่ ทำ MQTT Handshake และทำการ **Re-subscribe หัวข้อเดิม** ให้โดยอัตโนมัติ พร้อมส่งเหตุการณ์ `MQTT_EVENT_CONNECTED` กลับมา
     * **ข้อสังเกตในฝั่ง Wi-Fi Stack:** เลเยอร์ Wi-Fi ของ ESP-IDF จำเป็นต้องมีการดักจับเหตุการณ์ `WIFI_EVENT_STA_DISCONNECTED` ใน `wifi_event_handler` เพื่อเรียกสั่ง `esp_wifi_connect()` ให้เกาะกับ Access Point ใหม่ให้สำเร็จและได้รับ IP Address ก่อน จากนั้นตัว `esp-mqtt` ในพื้นหลังจึงจะสามารถกลับไปเชื่อมต่อกับ Broker ได้อย่างสมบูรณ์

### ข้อ 3: ในฟังก์ชัน `telemetry_task` เพราะเหตุใดหลังจากเรียก `cJSON_PrintUnformatted(root)` แล้วเราจึงจำเป็นต้องเรียกฟังก์ชัน `free(json_str)` และ `cJSON_Delete(root)` เสมอ? หากละเลยจะมีผลเสียอย่างไรต่อหน่วยความจำของ ESP32?
* **คำตอบ:**
  1. **เหตุผลที่ต้องเรียกฟังก์ชันทั้งสองคู่กันเสมอ:**
     * **`cJSON_Delete(root)`:** ฟังก์ชัน `cJSON_CreateObject()` และ `cJSON_Add...()` มีการจองหน่วยความจำแบบพลวัต (Dynamic Allocation ผ่าน `malloc`) เพื่อสร้างโครงสร้างข้อมูลแบบ Linked-list/Tree จึงจำเป็นต้องใช้ `cJSON_Delete(root)` เพื่อกวาดคืนหน่วยความจำของโหนดรากและโหนดลูกทั้งหมดกลับสู่ระบบ
     * **`free(json_str)`:** ฟังก์ชัน `cJSON_PrintUnformatted(root)` ทำการแปลงโครงสร้าง JSON ให้เป็นสตริงข้อความ โดยมีการ **จองพื้นที่หน่วยความจำก้อนใหม่แยกต่างหากบน Heap RAM** เพื่อเก็บข้อความสตริงนั้น เมื่อส่งข้อมูลผ่าน `esp_mqtt_client_publish()` เสร็จแล้ว จึงต้องเรียก `free(json_str)` เพื่อคืนหน่วยความจำสตริงก้อนนี้เช่นกัน
  2. **ผลเสียร้ายแรงหากละเลยไม่คืนหน่วยความจำ:**
     * เนื่องจาก `telemetry_task` ทำงานวนลูปตลอดเวลาทุกๆ 4 วินาที หากไม่มีการคืนหน่วยความจำ จะเกิดปัญหา **หน่วยความจำรั่วไหล (Memory Leak)** และ **หน่วยความจำแตกกระจาย (Heap Fragmentation)**
     * พื้นที่ Free Heap ของ ESP32 จะลดลงอย่างต่อเนื่องรอบละหลายร้อยไบต์ จนกระทั่งเข้าสู่ภาวะ **Out of Memory**
     * เมื่อหน่วยความจำหมด การจองหน่วยความจำในรอบถัดไปของ cJSON, ไดรเวอร์ Wi-Fi หรือ MQTT Stack จะล้มเหลว (ส่งค่า `NULL`) นำไปสู่การเกิด **System Crash / Kernel Panic (Guru Meditation Error / LoadProhibited / Abort)** และทำให้บอร์ดรีสตาร์ตตัวเองวนลูป (Boot Loop) อย่างต่อเนื่อง
