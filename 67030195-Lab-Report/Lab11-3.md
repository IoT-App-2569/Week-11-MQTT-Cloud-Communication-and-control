# ใบงานการทดลองที่ 11.3
### การสื่อสาร MQTT ความปลอดภัยสูงด้วย TLS และการยืนยันตัวตนสองทาง (mTLS) บน Mosquitto และ ESP-IDF
## การทดสอบและการตรวจสอบผลลัพธ์ (Testing & Verification)

1. แฟลชโปรแกรมลงบนบอร์ด ESP32
   ```powershell
   idf.py -p COMx flash monitor
   ```
2. สังเกตผลในหน้าต่าง Serial Monitor
   * บอร์ดเชื่อมต่อ Wi-Fi สำเร็จ
   * เริ่มกระบวนการจับมือ TLS `Connecting to 192.168.1.100:8883...`
   * หน้าจอรายงาน `MQTTS TLS Handshake Successful! Connected to Secure Broker.`
3. สังเกตหน้าต่าง Broker Log
   * Mosquitto จะพิมพ์ข้อความยืนยัน `Peer certificate verified: /C=TH/ST=Bangkok/O=IoT Node/CN=esp32-secure-node`
   * แสดงว่า Broker ได้ทำการตรวจความถูกต้องของใบรับรองบอร์ด ESP32 ผ่านเรียบร้อยแล้ว

## 5. คำถามท้ายการทดลอง (Post-Lab Questions)
1. เพราะเหตุใดในคำสั่งสร้าง Server CSR ค่า **Common Name (CN)** จึงต้องระบุเป็น IP Address หรือ Hostname ของ Broker ให้ตรงกันพอดี? หากระบุเป็นชื่ออื่นจะเกิดข้อผิดพลาดใดขึ้น?
   
   **ตอบ** ต้องระบุให้ตรงเพื่อป้องกันการโจมตีแบบคนกลาง (Man-in-the-Middle) หากระบุไม่ตรงกัน เมื่อ Client นำ IP หรือ Hostname ที่เชื่อมต่อไปเทียบกับ CN ในใบรับรองแล้วพบว่าไม่ตรงกัน จะเกิดข้อผิดพลาดทำให้กระบวนการ TLS Handshake ล้มเหลวและถูกตัดการเชื่อมต่อทันที
   
3. การยืนยันตัวตนแบบ **Mutual Authentication (mTLS)** แตกต่างจากการใช้ **HTTPS** ทั่วไปบนเว็บเบราว์เซอร์อย่างไรในประเด็นเรื่องใบรับรองฝั่ง Client?

   **ตอบ** HTTPS ทั่วไปบนเว็บเบราว์เซอร์จะทำการตรวจสอบใบรับรองเพื่อยืนยันตัวตนเฉพาะฝั่ง Server เท่านั้น (One-way) แต่ในระบบ mTLS (Mutual Authentication) จะมีการตรวจสอบทั้งสองทาง โดยฝั่ง Server จะบังคับให้ Client (ESP32) ต้องส่งใบรับรองส่วนตัว (Client Certificate) มาให้ตรวจสอบด้วย เพื่อยืนยันว่าอุปกรณ์นั้นได้รับอนุญาตจริง
   
5. หากมีผู้ไม่หวังดีขโมยไฟล์เฟิร์มแวร์ไบนารี (`.bin`) ของบอร์ด ESP32 ไปได้ เขาจะสามารถกู้คืนไฟล์ `client.key` ได้หรือไม่ และในระบบ IoT เชิงพาณิชย์เรามีฮาร์ดแวร์ความปลอดภัยใด (เช่น ESP32 Secure Boot / Flash Encryption / Digital Signature Peripheral) มาช่วยแก้ไขปัญหานี้?

   **ตอบ** สามารถกู้คืนไฟล์ `client.key` ได้ เนื่องจากในใบงานนี้ไฟล์ client.key ถูกฝังลงในไบนารีเป็นข้อความธรรมดา (Plain text) ในระบบ IoT เชิงพาณิชย์สามารถป้องกันได้โดยเปิดใช้คุณสมบัติ Flash Encryption เพื่อเข้ารหัสข้อมูลทั้งหมดในหน่วยความจำแฟลช และใช้ Digital Signature Peripheral (DS) เพื่อประมวลผลการเข้ารหัสด้วย Private Key ในระดับฮาร์ดแวร์ ทำให้แอปพลิเคชันหรือผู้บุกรุกไม่สามารถอ่านค่ากุญแจที่แท้จริงออกมาจากหน่วยความจำได้
