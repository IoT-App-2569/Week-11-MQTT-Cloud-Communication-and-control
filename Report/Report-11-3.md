## คำถามท้ายการทดลอง (Post-Lab Questions)

**1. เพราะเหตุใดในคำสั่งสร้าง Server CSR ค่า Common Name (CN) จึงต้องระบุเป็น IP Address หรือ Hostname ของ Broker ให้ตรงกันพอดี? หากระบุเป็นชื่ออื่นจะเกิดข้อผิดพลาดใดขึ้น?**
**ตอบ:** เนื่องจากในขั้นตอนการทำ TLS Handshake ฝั่ง Client จะทำการตรวจสอบว่าใบรับรองที่ได้รับมานั้น เป็นของเซิร์ฟเวอร์ที่ตนเองตั้งใจจะเชื่อมต่อเข้าไปจริงๆ หรือไม่ โดยการนำ IP Address หรือ Hostname ที่ตั้งค่าไว้ในโค้ด ไปเทียบกับค่า Common Name  ในใบรับรอง หากชื่อไม่ตรงกัน Client จะมองว่าอาจเป็นการโจมตีแบบสวมรอย และจะตัดการเชื่อมต่อทันที พร้อมแจ้งข้อผิดพลาดประเภท Hostname Mismatch หรือ Certificate Verification Failed

**2. การยืนยันตัวตนแบบ Mutual Authentication (mTLS) แตกต่างจากการใช้ HTTPS ทั่วไปบนเว็บเบราว์เซอร์อย่างไรในประเด็นเรื่องใบรับรองฝั่ง Client?**
**ตอบ:** การใช้ HTTPS ทั่วไปบนเว็บเบราว์เซอร์จะเป็นการยืนยันตัวตนแบบ "ทางเดียว" คือ Client จะตรวจสอบใบรับรองของ Server เท่านั้น เพื่อให้แน่ใจว่าเป็นเว็บไซต์จริง แต่ Server จะไม่ตรวจสอบใบรับรองของ Client
ส่วน **mTLS** จะเป็นการยืนยันตัวตนแบบ "สองทาง" คือ นอกจาก Client จะตรวจใบรับรองของ Server แล้ว ฝั่ง Server ก็จะบังคับให้ Client ต้องส่งใบรับรองของตนเองมาให้ตรวจด้วย (`require_certificate true`) หาก Client ไม่มีใบรับรองที่ถูกต้อง Server ก็จะปฏิเสธการเชื่อมต่อนั้นทันที

**3. หากมีผู้ไม่หวังดีขโมยไฟล์เฟิร์มแวร์ไบนารี (`.bin`) ของบอร์ด ESP32 ไปได้ เขาจะสามารถกู้คืนไฟล์ `client.key` ได้หรือไม่ และในระบบ IoT เชิงพาณิชย์เรามีฮาร์ดแวร์ความปลอดภัยใดมาช่วยแก้ไขปัญหานี้?**
**ตอบ:** **สามารถกู้คืนได้** หากไฟล์ `.bin` ไม่ได้ถูกเข้ารหัสไว้ ผู้ไม่หวังดีสามารถใช้โปรแกรมทำ Reverse Engineering เปิดดูข้อมูลไบนารีและดึงข้อความ `client.key` ออกมาได้อย่างง่ายดาย 
ในระบบ IoT เชิงพาณิชย์จึงต้องใช้ฟีเจอร์ความปลอดภัยระดับฮาร์ดแวร์ของ ESP32 เข้ามาช่วย เช่น:
- **Flash Encryption:** เข้ารหัสข้อมูลทั้งหมดที่เก็บบนหน่วยความจำ Flash
- **Digital Signature Peripheral:** นำ Private Key ไปเก็บไว้ใน Hardware eFuses ของชิปอย่างถาวร ซึ่งซอฟต์แวร์ไม่สามารถอ่านค่า Key ออกมาได้เลย ทำหน้าที่แค่ออกคำสั่งให้ฮาร์ดแวร์ช่วยเซ็นชื่อ ทางคริปโทกราฟีให้เท่านั้น
