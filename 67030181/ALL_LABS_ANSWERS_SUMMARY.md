## ใบงานที่ 11.1: Mosquitto Broker Setup & MQTT Fundamentals

### ข้อ 1: เพราะเหตุใดสัญลักษณ์ `#` จึงต้องวางไว้ที่ตำแหน่งท้ายสุดของ Topic เสมอ? หากกำหนด Topic Filter เป็น `home/#/light` จะเกิดข้อผิดพลาดอย่างไร?
**ตอบ:**  
เพราะว่าตัว `#` ในโปรโตคอล MQTT มันคือ **Multi-level Wildcard** ซึ่งมีความหมายว่า *"ให้ครอบคลุมทุกระดับชั้นย่อยนับตั้งแต่จุดนี้ยาวไปจนถึงปลายสุดของ Topic"* ครับ ในเมื่อมันกวาดเรียบไปจนสุดทางแล้ว ตามหลักการมันจึงต้องอยู่ตัวสุดท้ายเสมอ จะมีอะไรมาเขียนต่อท้ายมันอีกไม่ได้

ถ้าเราไปฝืนพิมพ์เป็น `home/#/light`:
- ตัว Broker จะมองว่าเราเขียนรูปแบบ Topic ผิดไวยากรณ์ (Syntax Error) ทันทีครับ
- ตอนที่ Client ส่งคำสั่ง Subscribe ไป ตัว Broker จะปฏิเสธไม่ยอมรับ โดยในมาตรฐาน MQTT 3.1.1 อาจจะตัดสายทิ้ง หรือตอบ `SUBACK` ที่เป็นรหัสล้มเหลว (`0x80`) และใน MQTT 5.0 ก็จะแจ้งเตือนชัดเจนเลยว่า `Topic Filter Invalid (0x8F)` ทำให้เราจะไม่ได้รับข้อความอะไรเลยจากหัวข้อนี้

### ข้อ 2: ในระบบงานติดตามยานพาหนะ (GPS Tracking) ที่ส่งพิกัดรถยนต์ทุกๆ 1 วินาที ท่านคิดว่าควรเลือกระดับ QoS ใดระหว่าง QoS 0, 1 หรือ 2 เพราะเหตุใด?
**ตอบ:**  
ควรเลือกใช้ **QoS 0 (At Most Once)** ครับ ด้วยเหตุผลตามการใช้งานจริงดังนี้:
1. **ข้อมูลส่งถี่มากอยู่แล้ว:** ตัวกล่อง GPS ส่งพิกัดใหม่ทุกๆ 1 วินาที ถ้าเกิดรถวิ่งลงอุโมงค์หรือสัญญาณเน็ต 4G/5G กระตุกไปแค่จังหวะนั้น แล้วพิกัดของวินาทีนั้นหายไป ก็ไม่เป็นปัญหาเลยครับ เพราะอีกแค่ 1 วินาทีถัดไป พิกัดใหม่ล่าสุดก็จะถูกส่งขึ้นมาแทนที่ทันที ไม่จำเป็นต้องย้อนส่งของเก่า
2. **ป้องกันปัญหารถติดคอขวด (Queue Jamming):** ถ้าเราไปใช้ QoS 1 ตอนที่เน็ตหลุด ตัวอุปกรณ์จะไม่ได้รับ `PUBACK` มันก็จะพยายามส่งซ้ำของเก่าวนไปเรื่อยๆ พอรถโผล่ออกจากอุโมงค์ ข้อมูลเก่าที่ค้างอยู่จะทะลักเข้าเซิร์ฟเวอร์พร้อมกันหมด ทำให้พิกัดบนหน้าจอแผนที่กระตุกหรือวิ่งย้อนไปย้อนมา
3. **ประหยัดเน็ตซิมและแบตเตอรี่:** QoS 0 มีขนาดหัวแพ็กเก็ตเล็กสุด (แค่ 2 ไบต์) และไม่ต้องส่งตอบรับสองทาง ช่วยประหยัดค่าเน็ตซิมการ์ด IoT และกินไฟน้อยที่สุด

### ข้อ 3: หาก Client ส่งแพ็กเก็ต `DISCONNECT` ไปยัง Broker อย่างถูกต้องก่อนปิดโปรแกรม ข้อความ Last Will and Testament (LWT) จะถูกเผยแพร่ออกไปหรือไม่ เพราะเหตุใด?
**ตอบ:**  
**ไม่ถูกส่งออกไปแน่นอนครับ**  
เพราะว่าฟังก์ชัน LWT (พินัยกรรมฉุกเฉิน) เขาตั้งใจออกแบบมาไว้ใช้ตรวจจับ **"เหตุการณ์ผิดปกติที่เครื่องดับไปโดยไม่ได้ตั้งใจ"** เท่านั้น เช่น อยู่ดีๆ บอร์ดไฟดับ, ชิปค้าง, หรือสายแลนหลุดกะทันหัน

แต่ถ้าโปรแกรมของเราปิดตัวลงอย่างถูกต้อง ตัว Client จะส่งแพ็กเก็ต `DISCONNECT` ไปบอก Broker ล่วงหน้าก่อน พอด้าน Broker ได้รับแพ็กเก็ตนี้ ก็จะเข้าใจทันทีว่า *"อ๋อ ฝั่งนี้เขาขอปิดการเชื่อมต่อตามปกตินะ"* ตัว Broker ก็จะทำการ **ลบข้อความ LWT ที่ฝากไว้ออกทิ้งทันที** แล้วค่อยปิดการเชื่อมต่อ ข้อความ LWT จึงไม่มีทางถูกส่งออกไปหาใคร

### ข้อ 4: Retained Message มีประโยชน์อย่างไรในการออกแบบระบบแดชบอร์ด Smart Home สำหรับผู้ใช้งานที่เพิ่งเปิดแอปพลิเคชันขึ้นมาเป็นครั้งแรก?
**ตอบ:**  
มีประโยชน์มากตรงที่ทำให้ **แอปพลิเคชันแสดงสถานะจริงของบ้านได้ทันทีที่เปิดแอปขึ้นมา** ครับ  
เพราะถ้าเป็น MQTT ปกติทั่วไป ถ้าไม่มีใครกดสวิตช์ไฟหรือเซนเซอร์ไม่ได้ส่งข้อมูลเข้ามาตอนนั้น Broker ก็จะไม่มีข้อมูลอะไรส่งให้แอปเลย พอเราเพิ่งเปิดแอปบนมือถือขึ้นมา หน้าจอก็จะขึ้นเป็นค่าว่างๆ หรือหมุนติ้วๆ รอโหลด ไม่รู้ว่าตอนนี้ไฟดวงไหนเปิดหรือปิดอยู่

แต่ถ้าเราตั้งค่า Retain ไว้ ตัว Broker จะคอยจำสถานะล่าสุดของแต่ละสวิตช์ไว้ในระบบเสมอ ทันทีที่เราเปิดแอปมือถือและกดเชื่อมต่อเข้า Broker ตัว Broker จะเด้งส่งข้อความล่าสุด (เช่น `home/light/state = ON`) ให้แอปนำไปแสดงผลบนสวิตช์ไฟได้ทันที โดยไม่ต้องรอให้มีใครไปกดเปิดปิดไฟรอบใหม่

## ใบงานที่ 11.2: ESP32 MQTT Client Telemetry & Control

### ข้อ 1: เพราะเหตุใดเราจึงต้องส่งข้อความสถานะ `iot/node01/status = "online"` ด้วยแฟล็ก `retain = 1` ควบคู่กับการตั้งค่า Last Will and Testament (LWT) ว่า `"offline"`?
**ตอบ:**  
เพื่อให้อุปกรณ์มีสถานะที่ตรงกับความเป็นจริงในโลกตลอดเวลาครับ:
1. **ตอนที่บอร์ดต่อติด:** พอบอร์ด ESP32 ต่อเข้ากับ Broker สำเร็จปุ๊บ ตัวบอร์ดจะรีบส่งข้อความบอกว่าตัวเอง `online` พร้อมสั่ง `retain = 1` ทันที ใครก็ตามที่เปิดหน้า Dashboard ขึ้นมาดูตอนไหน ก็จะเห็นทันทีว่าบอร์ดนี้พร้อมทำงานอยู่
2. **ตอนที่บอร์ดดับกะทันหัน:** ถ้าบอร์ดเกิดไฟดับ ถูกถอดปลั๊ก หรือ Wi-Fi ขาด ตัวบอร์ดมันไม่มีทางส่งบอกใครได้ แต่ Broker ที่จับเวลาดูอยู่จะรู้ว่าขาดการติดต่อ Broker ก็จะหยิบเอาข้อความ LWT ที่เราตั้งไว้ล่วงหน้าว่า `offline` (ที่สั่ง retain ไว้เหมือนกัน) ส่งมาทับที่หัวข้อเดิมให้ทันที
3. **ป้องกันอาการบอร์ดผีสิง (Zombie Device):** ผลก็คือหน้าจอ Dashboard ของเราจะไม่มีทางแสดงสถานะหลอกว่าอุปกรณ์ยังออนไลน์อยู่ ทั้งๆ ที่บอร์ดพังไปแล้ว ช่วยให้ระบบมีความน่าเชื่อถือ 100%

### ข้อ 2: หากเครือข่าย Wi-Fi หลุดชั่วคราว คอมโพเนนต์ `esp-mqtt` มีพฤติกรรมการจัดการอย่างไร และเมื่อสัญญาณกลับมา โค้ดจำเป็นต้องเรียกฟังก์ชันเชื่อมต่อใหม่ด้วยตนเองหรือไม่?
**ตอบ:**  
ตัวคอมโพเนนต์ `esp-mqtt` ของ ESP-IDF **มีระบบวนลูปเชื่อมต่อใหม่อัตโนมัติ (Auto-reconnect) ฝังอยู่ในตัวอยู่แล้วครับ เราไม่ต้องเขียนคำสั่งสั่งต่อ MQTT ใหม่เองเลย**

- ตอนที่ Wi-Fi หลุด ตัวสแตกเครือข่ายจะแจ้งเตือนเข้ามา แล้ว `esp-mqtt` จะยิง Event บอกว่า `MQTT_EVENT_DISCONNECTED` จากนั้นตัวมันจะเข้าสู่ลูปนับถอยหลังรอเพื่อพยายามต่อเข้าไปใหม่เรื่อยๆ
- สิ่งที่เราต้องเขียนในโปรแกรม มีแค่การจัดการฝั่ง **Wi-Fi Event Handler** เท่านั้น คือถ้าสัญญาณ Wi-Fi ขาด (`WIFI_EVENT_STA_DISCONNECTED`) ก็ให้สั่ง `esp_wifi_connect()` ซ้ำ
- พอบอร์ดเชื่อมต่อ Wi-Fi ติดและได้ IP จากเราเตอร์กลับมาเมื่อไหร่ ตัว `esp-mqtt` จะรู้ได้เองทันที และจะวิ่งกลับไปเชื่อมต่อ Broker พร้อมทั้งสมัคร Subscribe หัวข้อเดิมคืนให้ทั้งหมดแบบอัตโนมัติ

### ข้อ 3: ในฟังก์ชัน `telemetry_task` เพราะเหตุใดหลังจากเรียก `cJSON_PrintUnformatted(root)` แล้วเราจึงจำเป็นต้องเรียกฟังก์ชัน `free(json_str)` และ `cJSON_Delete(root)` เสมอ? หากละเลยจะมีผลเสียอย่างไรต่อหน่วยความจำของ ESP32?
**ตอบ:**  
เพราะว่าไลบรารี `cJSON` มันทำงานโดยการจองพื้นที่แรมในส่วน Heap ผ่านฟังก์ชัน `malloc()` 
1. ตัวโครงสร้างต้นไม้ JSON ที่เราสร้างขึ้นมาผ่านคำสั่ง `cJSON_CreateObject()` พอเรานำไปแปลงเป็นข้อความเสร็จแล้ว เราต้องสั่ง **`cJSON_Delete(root)`** เพื่อคืนพื้นที่แรมของโครงสร้างข้อมูลทั้งหมดกลับคืนสู่ระบบ
2. ส่วนฟังก์ชัน **`cJSON_PrintUnformatted(root)`** มันจะไปจองแรมก้อนใหม่อีกก้อนหนึ่งเพื่อใช้เก็บข้อความสตริง JSON ตัวแปร `json_str` จึงเป็นแรมที่แยกต่างหากออกมา เราเลยต้องสั่ง **`free(json_str)`** เพื่อล้างสตริงนี้ทิ้งด้วย

**ผลเสียถ้ารั่วไหล (Memory Leak):**  
เนื่องจากฟังก์ชันนี้ทำงานวนลูปส่งข้อมูลทุกๆ 4 วินาทีตลอดเวลา ถ้าเราลืมคืนแรม แค่ชั่วโมงเดียว แรมจะรั่วหายไปหลายร้อยกิโลไบต์ ซึ่งบอร์ด ESP32 มีแรมว่าง (Heap) ให้ใช้งานแค่ประมาณ 200–300 KB เท่านั้น พอแรมหมดเกลี้ยง บอร์ดจะสั่งจองแรมไม่ได้ เกิด Error เป็น **Guru Meditation Error (LoadProhibited)** แล้วบอร์ดก็จะแครชและรีบูตตัวเองวนไปเรื่อยๆ จนระบบพัง ใช้งานจริงไม่ได้

## ใบงานที่ 11.3: MQTTS TLS & Mutual Authentication Security

### ข้อ 1: เพราะเหตุใดในคำสั่งสร้าง Server CSR ค่า Common Name (CN) จึงต้องระบุเป็น IP Address หรือ Hostname ของ Broker ให้ตรงกันพอดี? หากระบุเป็นชื่ออื่นจะเกิดข้อผิดพลาดใดขึ้น?
**ตอบ:**  
เพราะว่าในขั้นตอนการตรวจสอบความปลอดภัยของโปรโตคอล TLS (เรียกว่า Hostname Verification) ตัวบอร์ด ESP32 ไม่ได้ตรวจดูแค่ว่าใบรับรองถูกเซ็นโดย Root CA หรือไม่ แต่ตัวบอร์ดจะเอา **IP Address หรือ Hostname ที่เราสั่งเชื่อมต่อเข้าไป (เช่น `192.168.1.111`) ไปเทียบกับชื่อ Common Name (CN) ที่ระบุไว้ในใบรับรองของ Server ด้วยครับ** เพื่อป้องกันไม่ให้มีแฮกเกอร์เอาใบรับรองที่ถูกต้องของเครื่องอื่นมาสวมรอยหลอกเรา

ถ้าเราไประบุเป็นชื่ออื่น (เช่น บอร์ดต่อเข้า `192.168.1.111` แต่ใบรับรองระบุ CN เป็น `mybroker.local` หรือ IP อื่น) ตัว ESP32 จะมองว่าเซิร์ฟเวอร์นี้เป็นของปลอมทันที แล้วจะฟ้อง Error ว่า `MBEDTLS_ERR_X509_CERT_VERIFY_FAILED` หรือ `BADCERT_CN_MISMATCH` ส่งผลให้การจับมือ TLS Handshake ล้มเหลว และบอร์ดจะตัดสายทิ้งทันที ไม่ยอมส่งข้อมูลเด็ดขาด

### ข้อ 2: การยืนยันตัวตนแบบ Mutual Authentication (mTLS) แตกต่างจากการใช้ HTTPS ทั่วไปบนเว็บเบราว์เซอร์อย่างไรในประเด็นเรื่องใบรับรองฝั่ง Client?
**ตอบ:**  
ความแตกต่างสำคัญที่สุดอยู่ที่ **"ใบรับรองของฝั่ง Client"** ครับ:
- **HTTPS ทั่วไป (One-way TLS):** มีแค่เว็บเซิร์ฟเวอร์ฝั่งเดียวที่มีใบรับรอง ส่วนตัวเราที่เปิดเว็บเบราว์เซอร์ไม่ต้องมีใบรับรองอะไรเลย ใครในโลกก็เปิดหน้าเว็บได้ แล้วค่อยไปล็อกอินด้วย Username กับ Password เอาทีหลังบนหน้าเว็บ
- **mTLS ในงาน IoT (Two-way TLS):** บังคับว่า **ทั้งสองฝั่งต้องมีใบรับรองดิจิทัลคู่กัน** คือนอกจาก ESP32 จะตรวจใบรับรองของโบรกเกอร์แล้ว ฝั่งโบรกเกอร์ก็จะขอดูใบรับรองของบอร์ด (`client.crt`) ด้วยเช่นกัน ถ้าอุปกรณ์ตัวไหนไม่มีใบรับรองที่ถูกเซ็นจาก Root CA ตัวโบรกเกอร์จะตัดการเชื่อมต่อทิ้งตั้งแต่แรกเลย ทำให้ไม่มีใครสามารถแอบต่อเข้ามาได้ และไม่ต้องกลัวปัญหาเรื่องการโดนเดารหัสผ่าน

### ข้อ 3: หากมีผู้ไม่หวังดีขโมยไฟล์เฟิร์มแวร์ไบนารี (`.bin`) ของบอร์ด ESP32 ไปได้ เขาจะสามารถกู้คืนไฟล์ `client.key` ได้หรือไม่ และในระบบ IoT เชิงพาณิชย์เรามีฮาร์ดแวร์ความปลอดภัยใด (เช่น ESP32 Secure Boot / Flash Encryption / Digital Signature Peripheral) มาช่วยแก้ไขปัญหานี้?
**ตอบ:**  
**กู้คืนได้ง่ายมากครับ** เพราะว่าในการเขียนโปรแกรมทั่วไป คำสั่ง `EMBED_TXTFILES` มันเอาข้อความใน `client.key` ไปวางแปะไว้ในเนื้อไฟล์ `.bin` แบบตัวหนังสือธรรมดาเลย ถ้าใครได้ไฟล์ไบนารีไป แค่เปิดดูด้วยโปรแกรมอ่าน Text หรือพิมพ์คำสั่ง `strings` หาคำว่า `BEGIN RSA PRIVATE KEY` ก็สามารถคัดลอกเอากุญแจลับออกไปใช้สวมรอยเป็นอุปกรณ์ของเราได้ทันทีครับ

ในผลิตภัณฑ์จริงเชิงพาณิชย์ จึงต้องเปิดใช้งานระบบความปลอดภัยระดับฮาร์ดแวร์ของ ESP32 เข้ามาช่วย 3 อย่าง:
1. **Flash Encryption:** ใช้ชิปฮาร์ดแวร์เข้ารหัสข้อมูลทั้ง Flash ด้วย AES-256 กุญแจถอดรหัสจะถูกฝังตายอยู่ใน eFuse ข้างในตัวชิป ใครถอดชิปออกไปดัมป์ข้อมูลก็จะได้ไปแต่ข้อมูลขยะที่อ่านไม่ออก
2. **Secure Boot:** คอยตรวจเช็กลายเซ็นดิจิทัลของโปรแกรมก่อนบูตทุกครั้ง เพื่อป้องกันไม่ให้ใครเอาเฟิร์มแวร์แฮกมาแฟลชทับ
3. **Digital Signature Peripheral (DS Peripheral):** อันนี้ดีที่สุด คือตัว ESP32 จะมีวงจรถอดรหัสลับในตัว กุญแจส่วนตัวจะถูกซ่อนไว้ในฮาร์ดแวร์ แม้แต่โค้ดของบอร์ดเองก็อ่านกุญแจออกมาดูไม่ได้ เวลาจะต่อ mTLS ตัววงจรนี้จะช่วยเซ็นชื่อให้เอง ทำให้กุญแจไม่มีวันหลุดออกมาข้างนอกได้ 100%

### ข้อ 1: ในสถาปัตยกรรม ESP RainMaker กระบวนการ Assisted Claiming ช่วยแก้ปัญหาเรื่องการติดตั้งใบรับรองความปลอดภัย (Security Certificates) บนอุปกรณ์ในขั้นตอนพัฒนาต้นแบบได้อย่างไร?
**ตอบ:**  
ช่วยแก้ปัญหาความยุ่งยากในการติดตั้งกุญแจได้อย่างมากครับ  
เพราะปกติแล้วเวลาจะต่อบอร์ดเข้ากับระบบคลาวด์ AWS IoT Core อุปกรณ์ทุกตัวต้องมีใบรับรองและกุญแจเฉพาะตัวฝังอยู่ก่อน ถ้าเป็นวิธีเดิมตอนทดลองทำโครงงาน เราต้องมานั่งใช้ OpenSSL สร้างกุญแจทีละใบ แล้วต้องมาคอยแฟลชลงทีละบอร์ด ซึ่งเสียเวลาและยุ่งยากมาก

แต่ระบบ **Assisted Claiming** ของ RainMaker คือเราแค่แฟลชโปรแกรมเปล่าลงบอร์ด แล้วเปิดแอปพลิเคชันบนมือถือไปสแกน QR Code เพื่อเชื่อมต่อผ่านบลูทูธ (BLE) ตัวแอปมือถือของเราที่มีอินเทอร์เน็ตอยู่แล้ว จะวิ่งไปขอใบรับรองจากคลาวด์ของ RainMaker มาให้ แล้วส่งต่อผ่านท่อบลูทูธไปบันทึกลงในหน่วยความจำ NVS Flash ของบอร์ด ESP32 ให้อัตโนมัติทันที ทำให้เราไม่ต้องมานั่งสร้างหรือจัดการไฟล์กุญแจด้วยตัวเอง

### ข้อ 2: เพราะเหตุใดฟังก์ชัน `write_cb` จึงต้องเรียกคำสั่ง `esp_rmaker_param_update_and_report()` ทุกครั้งที่มีการเปลี่ยนแปลงค่าพารามิเตอร์?
**ตอบ:**  
เพราะเป็นการส่งข้อความกลับไปบอกคลาวด์ว่า **"ตัวฮาร์ดแวร์จริงๆ ได้ทำงานตามคำสั่งเรียบร้อยแล้วนะ"** ครับ
1. คำสั่งที่ผู้ใช้กดมาจากหน้าจอมือถือ มันเป็นแค่สิ่งที่ผู้ใช้ต้องการ (Desired State) เช่น สั่งเปิดไฟ
2. พอบอร์ดรับคำสั่งเข้ามาในฟังก์ชัน `write_cb` แล้วสั่งให้ขา GPIO จ่ายไฟให้หลอดไฟติดจริงๆ สำเร็จ เราจึงต้องเรียกคำสั่งนี้เพื่อรายงานสถานะจริง (Reported State) กลับไปที่คลาวด์
3. พอคลาวด์ได้รับสถานะจริง คลาวด์ก็จะส่งต่อไปอัปเดตหน้าจอแอปมือถือให้สวิตช์เด้งเปิดตามความเป็นจริงทันที ทำให้หน้าจอไม่ขึ้นค้าง และถ้ามีคนอื่นในบ้านเปิดแอปดูอยู่ด้วย ทุกคนก็จะได้เห็นสถานะตรงกันแบบ Real-time
