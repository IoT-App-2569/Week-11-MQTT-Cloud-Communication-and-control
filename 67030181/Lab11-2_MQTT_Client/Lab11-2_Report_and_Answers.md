# รายงานผลการทดลองและตอบคำถามท้ายการทดลอง ใบงานที่ 11.2
## เรื่อง: การพัฒนา ESP32 MQTT Client เพื่อรายงานข้อมูลเซนเซอร์ Telemetry และรับคำสั่งควบคุมอุปกรณ์ระยะไกล

**รหัสนักศึกษา:** 67030181  
**วิชา:** IoT Cloud Communication and Control (สัปดาห์ที่ 11)  

---

## 1. วัตถุประสงค์การทดลอง
1. สามารถกำหนดค่าและใช้งานคอมโพเนนต์ `esp-mqtt` บนเฟรมเวิร์ก ESP-IDF เพื่อสร้างการเชื่อมต่อกับ MQTT Broker ได้
2. สามารถเขียน Event Handler เพื่อจัดการเหตุการณ์เครือข่าย `MQTT_EVENT_CONNECTED`, `MQTT_EVENT_DATA`, `MQTT_EVENT_DISCONNECTED` ได้อย่างสมบูรณ์
3. สามารถพัฒนา FreeRTOS Task ร่วมกับคอมโพเนนต์ `esp_adc` และไลบรารี `cJSON` เพื่ออ่านค่าแรงดันแอนะล็อกและส่งข้อมูล Telemetry JSON ขึ้นสู่ Broker ตามรอบเวลาที่กำหนด
4. สามารถถอดรหัสคำสั่งควบคุม (ทั้ง Plaintext และ JSON Payload) จาก Broker แล้วนำไปควบคุมสถานะเอาต์พุต GPIO ของ LED พร้อมทั้งตอบรับสถานะกลับ (State Acknowledgement)
5. เข้าใจและสามารถแก้ไขปัญหาทางปฏิบัติ เช่น ปัญหา Split-Brain Broker บนระบบปฏิบัติการ Windows และพฤติกรรมการลดระดับ QoS เมื่อ Subscribe ด้วย QoS ต่ำกว่า

## 2. การต่อวงจรและโครงสร้างฮาร์ดแวร์ (Hardware Wiring)

การทดลองนี้รองรับทั้งบอร์ด **ESP32 Classic (38-pin)** และ **ESP32-C3 (RISC-V)** โดยต่อวงจรดังตาราง:

| อุปกรณ์ภายนอก | ขาบนอุปกรณ์ | ขาเชื่อมต่อ ESP32 Classic | ขาเชื่อมต่อ ESP32-C3 | หน้าที่การทำงาน |
| :--- | :--- | :--- | :--- | :--- |
| **LED สีแดง/น้ำเงิน** | Anode (+) ผ่าน R 330Ω | **GPIO 2** (Onboard LED) | **GPIO 8** | ตัวแทน Actuator รับคำสั่งเปิด-ปิดจากระยะไกล |
| **LED** | Cathode (-) | **GND** | **GND** | กราวด์อ้างอิง |
| **Potentiometer 10k** | Wiper (ขากลาง) | **GPIO 34** (ADC1_CH6) | **GPIO 0** (ADC1_CH0) | เซนเซอร์ตรวจวัดแรงดันแอนะล็อก (0 - 3.3V) |
| **Potentiometer 10k** | ขาริมซ้าย / ขวา | **3.3V และ GND** | **3.3V และ GND** | แหล่งจ่ายไฟและกราวด์ |

```
         ESP32 Board                             Peripherals
       +-------------------+                       +--------------------------+
       |   GPIO 2 (or 8)   |---------------------->| LED (+ 330Ω Resistor)    |
       |   GPIO 34 (or 0)  |<----------------------| Potentiometer Wiper (ADC)|
       |              3.3V |---------------------->| VCC (3.3V)               |
       |               GND |---------------------->| GND                      |
       +-------------------+                       +--------------------------+
```

## 3. สรุปขั้นตอนการพัฒนาและผลการทดลอง

### 3.1 โครงสร้างซอฟต์แวร์ ESP-IDF
* กำหนด Dependencies ผ่าน `main/idf_component.yml`:
  ```yaml
  dependencies:
    espressif/cjson: '*'
    espressif/mqtt: '*'
  ```
* ใน `main/CMakeLists.txt` ได้เพิ่มคอมโพเนนต์ที่จำเป็นครบถ้วน ได้แก่ `mqtt`, `cjson`, `esp_wifi`, `esp_event`, `nvs_flash`, `esp_adc`, `esp_driver_gpio`
* โค้ดโปรแกรมใช้คำสั่ง Preprocessor Directives `#if CONFIG_IDF_TARGET_ESP32C3` เพื่อสลับการใช้งาน GPIO และ ADC Channel ระหว่างตระกูลชิปได้อย่างอัตโนมัติ

---

### 3.2 ผลการทดสอบ Telemetry Data
เมื่อเปิดโปรแกรม `mosquitto_sub` เพื่อดักฟังหัวข้อ `iot/node01/telemetry`:
```powershell
mosquitto_sub -h 192.168.1.111 -p 1883 -t "iot/node01/telemetry" -v
```
**ข้อมูลที่ได้รับจริงทุกๆ 4 วินาที:**
```text
iot/node01/telemetry {"node_id":"esp32-node01","adc_raw":1820,"voltage_v":1.466,"led_state":false,"uptime_ms":6855}
iot/node01/telemetry {"node_id":"esp32-node01","adc_raw":2150,"voltage_v":1.732,"led_state":false,"uptime_ms":10855}
```
* **การทดสอบหมุนก้าน Potentiometer:** เมื่อหมุนก้านปรับค่าไปทางขวา ค่า `adc_raw` เพิ่มขึ้นสู่ช่วง `3000-4095` และค่า `voltage_v` คำนวณได้สอดคล้องกับแรงดันจริง (สูงสุด 3.3V)

---

### 3.3 ผลการทดสอบคำสั่งควบคุมหลอดไฟ LED

#### 1. คำสั่งเปิดไฟ (Plaintext)
```powershell
mosquitto_pub -h 192.168.1.111 -p 1883 -t "iot/node01/cmd/led" -m "ON" -q 1
```
* **ผลลัพธ์:** หลอดไฟ LED ติดสว่างทันที และบอร์ด ESP32 ส่งสถานะตอบรับกลับมายังหัวข้อ `iot/node01/state/led` ว่า `{"led_state": true}`
* ในรอบ Telemetry ถัดไป ค่าฟิลด์ `"led_state"` เปลี่ยนจาก `false` เป็น `true` ทันที

#### 2. คำสั่งปิดไฟ (Plaintext)
```powershell
mosquitto_pub -h 192.168.1.111 -p 1883 -t "iot/node01/cmd/led" -m "OFF" -q 1
```
* **ผลลัพธ์:** หลอดไฟ LED ดับลงทันที และสถานะตอบรับรายงาน `{"led_state": false}`

#### 3. คำสั่งผ่าน JSON Payload
```powershell
mosquitto_pub -h 192.168.1.111 -p 1883 -t "iot/node01/cmd/led" -m "{\"state\": 1}" -q 1
```
* **ผลลัพธ์:** ฟังก์ชัน `mqtt_event_handler` ตรวจจับสตริง `\"state\": 1` ได้ถูกต้อง และสั่งเปิดหลอดไฟ LED

## 4. บันทึกการวิเคราะห์ปัญหาเชิงปฏิบัติ (Troubleshooting Analysis)

1. **ปัญหา Split-Brain Mosquitto Broker บน Windows:**  
   หากไม่ได้ปิด Windows Service `mosquitto` ตัวเบื้องหลังจะจองพอร์ต 1883 บน `127.0.0.1` ในขณะที่การรันใน Terminal จะจอง IP วงแลน `192.168.1.xxx` ทำให้คำสั่ง CLI ส่งไปไม่ถึง ESP32 ได้แก้ไขสำเร็จโดยการสั่ง `Stop-Service mosquitto` ก่อนเริ่มการทดลอง
2. **ประเด็นระดับ QoS บน MQTT Explorer:**  
   เมื่อตรวจสอบแพ็กเก็ตผ่าน MQTT Explorer จะพบว่าเป็น QoS 0 เสมอ แม้คำสั่ง `mosquitto_pub` จะระบุ `-q 1` ทั้งนี้เป็นไปตามกฎ **`Effective QoS = min(QoS_pub, QoS_sub)`** เนื่องจาก MQTT Explorer สมัครรับข้อมูลทุกหัวข้อ (`#`) ด้วย QoS 0 ทำให้ Broker ต้อง Downgrade แพ็กเก็ตลงมาเป็น QoS 0 ส่งให้ Explorer

## 5. คำถามท้ายการทดลอง (Post-Lab Questions)

### ข้อ 1: เพราะเหตุใดเราจึงต้องส่งข้อความสถานะ `iot/node01/status = "online"` ด้วยแฟล็ก `retain = 1` ควบคู่กับการตั้งค่า Last Will and Testament (LWT) ว่า `"offline"`?

**ตอบ:**  
เพื่อให้อุปกรณ์มีสถานะที่ตรงกับความเป็นจริงในโลกตลอดเวลาครับ:
1. **ตอนที่บอร์ดต่อติด:** พอบอร์ด ESP32 ต่อเข้ากับ Broker สำเร็จปุ๊บ ตัวบอร์ดจะรีบส่งข้อความบอกว่าตัวเอง `online` พร้อมสั่ง `retain = 1` ทันที ใครก็ตามที่เปิดหน้า Dashboard ขึ้นมาดูตอนไหน ก็จะเห็นทันทีว่าบอร์ดนี้พร้อมทำงานอยู่
2. **ตอนที่บอร์ดดับกะทันหัน:** ถ้าบอร์ดเกิดไฟดับ ถูกถอดปลั๊ก หรือ Wi-Fi ขาด ตัวบอร์ดมันไม่มีทางส่งบอกใครได้ แต่ Broker ที่จับเวลาดูอยู่จะรู้ว่าขาดการติดต่อ Broker ก็จะหยิบเอาข้อความ LWT ที่เราตั้งไว้ล่วงหน้าว่า `offline` (ที่สั่ง retain ไว้เหมือนกัน) ส่งมาทับที่หัวข้อเดิมให้ทันที
3. **ป้องกันอาการบอร์ดผีสิง (Zombie Device):** ผลก็คือหน้าจอ Dashboard ของเราจะไม่มีทางแสดงสถานะหลอกว่าอุปกรณ์ยังออนไลน์อยู่ ทั้งๆ ที่บอร์ดพังไปแล้ว ช่วยให้ระบบมีความน่าเชื่อถือ 100% ครับ

### ข้อ 2: หากเครือข่าย Wi-Fi หลุดชั่วคราว คอมโพเนนต์ `esp-mqtt` มีพฤติกรรมการจัดการอย่างไร และเมื่อสัญญาณกลับมา โค้ดจำเป็นต้องเรียกฟังก์ชันเชื่อมต่อใหม่ด้วยตนเองหรือไม่?

**ตอบ:**  
ตัวคอมโพเนนต์ `esp-mqtt` ของ ESP-IDF **มีระบบวนลูปเชื่อมต่อใหม่อัตโนมัติ (Auto-reconnect) ฝังอยู่ในตัวอยู่แล้วครับ เราไม่ต้องเขียนคำสั่งสั่งต่อ MQTT ใหม่เองเลย**

- ตอนที่ Wi-Fi หลุด ตัวสแตกเครือข่ายจะแจ้งเตือนเข้ามา แล้ว `esp-mqtt` จะยิง Event บอกว่า `MQTT_EVENT_DISCONNECTED` จากนั้นตัวมันจะเข้าสู่ลูปนับถอยหลังรอเพื่อพยายามต่อเข้าไปใหม่เรื่อยๆ
- สิ่งที่เราต้องเขียนในโปรแกรม มีแค่การจัดการฝั่ง **Wi-Fi Event Handler** เท่านั้น คือถ้าสัญญาณ Wi-Fi ขาด (`WIFI_EVENT_STA_DISCONNECTED`) ก็ให้สั่ง `esp_wifi_connect()` ซ้ำ
- พอบอร์ดเชื่อมต่อ Wi-Fi ติดและได้ IP จากเราเตอร์กลับมาเมื่อไหร่ ตัว `esp-mqtt` จะรู้ได้เองทันที และจะวิ่งกลับไปเชื่อมต่อ Broker พร้อมทั้งสมัคร Subscribe หัวข้อเดิมคืนให้ทั้งหมดแบบอัตโนมัติครับ

### ข้อ 3: ในฟังก์ชัน `telemetry_task` เพราะเหตุใดหลังจากเรียก `cJSON_PrintUnformatted(root)` แล้วเราจึงจำเป็นต้องเรียกฟังก์ชัน `free(json_str)` และ `cJSON_Delete(root)` เสมอ? หากละเลยจะมีผลเสียอย่างไรต่อหน่วยความจำของ ESP32?

**ตอบ:**  
เพราะว่าไลบรารี `cJSON` มันทำงานโดยการจองพื้นที่แรมในส่วน Heap ผ่านฟังก์ชัน `malloc()` ครับ
1. ตัวโครงสร้างต้นไม้ JSON ที่เราสร้างขึ้นมาผ่านคำสั่ง `cJSON_CreateObject()` พอเรานำไปแปลงเป็นข้อความเสร็จแล้ว เราต้องสั่ง **`cJSON_Delete(root)`** เพื่อคืนพื้นที่แรมของโครงสร้างข้อมูลทั้งหมดกลับคืนสู่ระบบ
2. ส่วนฟังก์ชัน **`cJSON_PrintUnformatted(root)`** มันจะไปจองแรมก้อนใหม่อีกก้อนหนึ่งเพื่อใช้เก็บข้อความสตริง JSON ตัวแปร `json_str` จึงเป็นแรมที่แยกต่างหากออกมา เราเลยต้องสั่ง **`free(json_str)`** เพื่อล้างสตริงนี้ทิ้งด้วย

**ผลเสียถ้ารั่วไหล (Memory Leak):**  
เนื่องจากฟังก์ชันนี้ทำงานวนลูปส่งข้อมูลทุกๆ 4 วินาทีตลอดเวลา ถ้าเราลืมคืนแรม แค่ชั่วโมงเดียว แรมจะรั่วหายไปหลายร้อยกิโลไบต์ ซึ่งบอร์ด ESP32 มีแรมว่าง (Heap) ให้ใช้งานแค่ประมาณ 200–300 KB เท่านั้น พอแรมหมดเกลี้ยง บอร์ดจะสั่งจองแรมไม่ได้ เกิด Error เป็น **Guru Meditation Error (LoadProhibited)** แล้วบอร์ดก็จะแครชและรีบูตตัวเองวนไปเรื่อยๆ จนระบบพัง ใช้งานจริงไม่ได้
